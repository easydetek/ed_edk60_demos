## 二、范围与非范围

### 包含（本期交付）

1. **工程骨架**：顶层 `CMakeLists.txt`（含目标芯片校验）、`sdkconfig.defaults`、`sdkconfig.defaults.esp32c6`。
2. **多 demo 机制**：`main/Kconfig.projbuild` 的 `choice APP_EDK60_DEMO` + `components/edk60_app/src/demo_dispatch.c` 编译期分派。
3. **板级支持包**：`components/edk60_board`（引脚宏 + LED / 按键 / I²C / 雷达电源 / 控制台 / 板卡信息）。
4. **15 个 demo**，分四组：
   - 基础外设组 5 个：`hello_board`、`blink`、`button`、`uart_echo`、`adc_read`
   - 无线组 4 个：`wifi_sta`、`wifi_softap`、`ble_uart`、`ble_scan`
   - 板载互动组 3 个：`radar_power`、`led_sequence`、`i2c_scan`
   - 低功耗与存储组 3 个：`deep_sleep`、`nvs_rw`、`usb_serial_bridge`
5. **雷达透传组 1 个**（用户追加需求，见 CR-08）：`radar_bridge` —— 雷达模组 → UART → 原生 USB 串口 → PC 上位机的**纯字节透传**，含接收脚/波特率自动识别、雷达电源控制、本地回环自测。
6. **构建工具**：`build_all.ps1`（逐 demo 独立 build 目录批量编译验证）。
7. **IDE 集成**：`.vscode/settings.json`、`.vscode/launch.json`、`docs/vscode-setup.md`。
8. **文档**：`README.md`、`docs/EDK60-pinmap.md`、`docs/project/*`。

### 不包含（本期明确不做，若要做需另立变更）

1. **单元测试与 CI/CD 流水线**：不引入 Unity 测试工程、不配置 GitHub Actions。理由：本期目标是「demo 示例库」而非产品固件。
2. **OTA / 分区表定制 / 安全启动**：不做 OTA demo、不做自定义分区表、不做固件签名。理由：与「板卡 demo」目标无关，且会改变烧录流程。
3. **上位机 App / 手机端 App**：只做板端固件；BLE/Wi-Fi 的验证用第三方工具（nRF Connect、串口助手）。
4. **修改硬件**：不改板、不飞线、不增减器件。所有引脚结论以现有原理图 V1.0 为准；实测有出入时只更新文档与风险登记册。
5. **物联云平台对接**：不接阿里云/AWS IoT/Home Assistant 等。
6. **性能基准与功耗实测报告**：`deep_sleep` 只给预期与测法，不产出实测功耗数据（需实验室万用表/功耗仪）。
7. **多版本 IDF 兼容**：只针对 ESP-IDF **v6.1**。v5.x 兼容不在范围内。

## 四、关键约束与假设

| 类型 | 内容 | 影响 | 验证/监控方式 | 失效后果 |
|---|---|---|---|---|
| **约束** | 主控固定为 ESP32-C6-MINI-1-N4，4MB Flash，无 PSRAM | 不能用 PSRAM 相关特性；分区表受限 | 编译时 `IDF_TARGET=esp32c6` 校验 | 需改板或换模组 |
| **约束** | 只支持 ESP-IDF v6.1 | API 与 v5.x 不同（如 LEDC 渐变、NimBLE 初始化、Kconfig 符号） | 所有编译在本机 v6.1 下验证 | 用户换版本需重新适配 |
| **约束** | 板载无 USB 转串口芯片 | 串口能力依赖 C6 原生 USB Serial/JTAG | `usb_serial_jtag` demo | 若无原生 USB，则需外接串口板 |
| **约束** | 雷达模组为插拔式，可能未插 | demo 必须能在无模组时安全运行 | `radar_power` 的静默诊断逻辑 | demo 崩溃或误报 |
| **约束** | 本机 PowerShell 默认禁止运行脚本 | 脚本需 `-ExecutionPolicy Bypass` | README/文档均写明调用方式 | 用户执行脚本失败 |
| **假设** | `U4.EN` 经 R2(10k) 下拉到 GND，因此 3.3V_RADAR **默认关闭**；IO15 输出高即使能 | 雷达电源控制与热插拔安全性 | 读图核实（2026-10-14）+ 上板实测（H-01/H-02） | 需改控制方式 |
| **假设** | 丝印 "L" 的橙色 LED4 由 IO15 直接驱动，可作雷达电源指示灯 | 上板验收手段（肉眼可见） | 上板实测（H-03） | 只能用万用表校验 |
| **假设** | IO15 输出 3.3V 高电平满足 AP7362 的 EN 高门限 | 雷达能否被软件使能 | 查 AP7362 datasheet + 上板实测（H-01） | 需加电平转换 |
| **假设** | IO12/IO13 在 MINI-1 模组上已引出且连到 USB-C | 「USB 转串口」成立的前提 | 插 USB 实测枚举（风险 H-05） | 该需求无法在本板实现 |
| **假设** | IO9(BOOT) 可用 `esp_sleep_enable_gpio_wakeup_on_hp_periph_powerdown` 唤醒 | `deep_sleep` 的按键唤醒方案 | 上板实测；失败则降级为定时器+EXT1 | 需引导用户用 IO0..IO5 跳线 |
| **假设** | 用户后续会自行上板烧录验证 | 交付物止于「编译通过 + 上板指引」 | 用户反馈 | 需追加实测支持 |

## 六、治理与决策机制

### 决策权矩阵（A=拍板 R=评审 C=提议 I=知会）

| 决策事项 | 提议 | 评审 | 拍板 | 是否升级用户 |
|---|---|---|---|---|
| 工程结构（组件划分、目录布局） | 项目经理 | 嵌入式工程师 | 项目经理 | 否 |
| demo 清单与优先级 | 项目经理 | 用户 | 项目经理 | **范围增减时升级** |
| 引脚结论（IO 分配、电气特性） | 硬件工程师 | 评审官 | 项目经理 | 与用户实测冲突时**必须** |
| demo 实现方案（API/协议选型） | 嵌入式工程师 | 项目经理 | 项目经理 | 否 |
| 编译不过的取舍（降级/换方案） | 项目经理 | 评审官 | 项目经理 | 影响 G2/G4 时**必须** |
| Git 提交与推送 | 项目经理 | — | **用户** | **必须**（对外动作） |
| 删除/覆盖既有文件 | 提议方 | 项目经理 | **用户** | **必须**（删除守则） |

### 升级给用户的四条硬规则

1. 需要用户才能提供的资源或授权（Git 推送、对外发布、硬件采购）。
2. 与章程目标/成功标准冲突的决定（如为编译通过而砍掉某个 demo）。
3. 跨角色无法收敛的争议，且影响进度或质量底线。
4. 不可逆决定（删除文件、改板建议、认证相关）。
