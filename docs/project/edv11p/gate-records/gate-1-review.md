## 一、总体结论（先给结论，后给证据）

**决策：GO-with-conditions（有条件放行）**

一句话理由：**"纯字节双向透传 + 不注入命令 + 控制台洁净靠'不产生字符'"这条桥接主干是可放行的**（机制有 IDF 源码级证据、有两次上板实测反例、帧校验工具离线自测可复现）；但**材料中存在 7 条必须在 P1/P2 收尾前闭环的 P1 问题**，其中三条属于"结论强度超过证据强度"（型号分支、斜装坐标系、供电缓解前提），若带着它们进入上板实测，最可能的结果不是"测不出来"，而是**测出来却归因错**（把能力边界问题误判成接线/固件问题，重复浪费现场时间）。

放行的边界（必须写进 Gate 记录，避免后续被扩大解释）：

1. 本次放行的是**桥接方案**与**验证方法**，**不是**"侧装 60° 轨迹正确"这一产品结论；
2. 本次放行**不等于**允许对外承诺"线上演示可用"——网页工具尚未经过真实浏览器目检与真机联调（见 §5-F、条件 C-10）；
3. 本次放行**不等于** R1/R12（风险登记册中 R≥15 的两条）已闭环，只等于"已给出结论 + 已明确闭环判据与责任人"（见 §2.4 第 3 条对登记册规则的解释）。

### 4.2 P1 详述（问题 / 证据 / 影响 / 建议动作 / 责任角色）

#### P1-01 型号分支：把"本地 hex 全为 -03"当成"手上模组是 -03"

- **问题**：hw 文档 §0/§3.1 直接断言"手上的模组 = EDV11P-N-03"，其唯一依据是"仓库内 6 个 hex 全部含跌倒判据串"。这是**非充分推理**：本地 hex 集合只说明"手上有哪些固件文件"，不说明"插在板上的模组是哪个分支"（-02 的固件根本不在本地，正好不会被解析到）。反过来，用户口头确认"是 -02"也不构成证据。**当前正确状态是"型号未定"，而不是任何一侧的结论。**
- **证据**：
  - `hw-wiring-and-firmware.md:19`（§0 结论"手上的模组是 EDV11P-N-03"）、`:184`（§3.1 同断言）
  - `hw-wiring-and-firmware.md:198-217`（§3.3 hex 解析表 —— 证据本身只支持"本地无 -02 固件"）
  - `hw-wiring-and-firmware.md:196`（0x70"仅人数统计产品支持"）、`:265`（"不是软件能绕过去的"）
  - `risk-register.md:17`（R11 P 由 3 降为 **1**，触发信号写"上板后…"，缓解写"**用户已确认手持模组为 -02**（2026-10-21）"）
  - `dispatch-log.md:22`（DEC-06 同口径）
  - `analysis-bridge-feasibility.md:597`（U2 仍把型号列为未确认项，与 R11 降级自相矛盾）
- **影响**：R11 的 I=5（若为 -03 则 G2/G3「轨迹正确」根本不可达），P 从 3 降到 1 使 R 从 15 掉到 5，**直接逃出了"R≥15 必须逐条给结论"的升级阈值**。也就是说：一次口头确认，把一个"可能让整个 demo 失效"的风险，从必须评审的清单里移走了。这是 Gate 评审最需要拦住的一类问题。
- **建议动作**：① 型号状态统一改为"**未定（待上板回读）**"；② R11 的 P 恢复为 ≥3（I 保持 5，R=15）；③ 上板流程第一步固定为 `GET 0x02`（帧 `45 44 00 0B 00 01 A0 02 00 00 37`，`hw:252`），并把**原始应答字节**写进 Gate-2 记录；④ 预先写死三条分支处置：回读 `EDV11P_VB,<ver>,<id>` 且后续收到 0x70 → 通过；回读为 -03 或无 0x70 → 立即升级用户，二选一（索取 -02 模组/固件，或改做 0x73 过渡 demo）；完全无应答 → 先按 §5-E 排查 TX 通路，不得直接归因"模组不支持"。
- **责任角色**：硬件工程师（主）+ 项目经理（风险册与升级路径）

- **问题**：web 设计文档明确写"固件已完成 XYZ 转换、上位机不重复旋转"，依据是**参考上位机的一行注释**；hw 文档明确写"协议 0x20~0x33 无任何倾角/旋转参数、说明书写水平安装 0°、侧装无书面依据、待实测"。两者只能有一个为真，但 `recipe-brief.md` 已经把 web 侧的口径标注为"**已核实**"——一旦 recipe 按此写，会把一个未经任何硬件验证的断言发布到 docs.easydetek.com。

#### P1-04 供电：缓解方案的前提不成立 + 背压余量与代码自述不符

- **问题 1（前提不成立）**：缓解方案 A 写"DC-005 接 5V/≥2A，**USB-C 只接 PC 做数据**"（`hw:162`）。但插 USB-C 到 PC 时 **VBUS 必然存在**——"只传数据"在物理上不成立（除非用 VBUS 断开的定制线）。真正决定成败的是 U2（LM66100 理想二极管）的**优先级与反灌阻断行为**，而这正是 T-09"待实测"（`hw:408`）。换言之：**头号风险的缓解方案建立在一个未验证的器件行为上，且材料的措辞会让执行者以为"拔掉就不担心了"。**
- **问题 2（余量自述与代码矛盾）**：代码允许单次 USB 写阻塞 100 ms、连续重试 20 次 + 5 ms 退避（`demo...edv11p.c:201-203,314-322`）⇒ 最坏 **≈2.1 s** 不消费 UART。而 UART RX 环形缓冲 8192 B @921600 ≈ **88.9 ms**（`analysis:178`）。代码注释却写"余量 ≥ 8 倍"（`:99-102`）。**算术不成立**：一旦主机停顿超过 ~89 ms，UART 环形缓冲即静默丢字节（`analysis:216` 自己也承认这是"静默丢字节"）。而该事件**没有任何计数器**（`br_stats_t` 里只有 `usb_tx_dropped`/`usb_wr_stalls`，无 UART 溢出计数，`:228-237`），且诊断默认关闭（`sdkconfig.defaults...:54`）。
- **证据**：`hw:18`（头号风险）、`:134`（LDO 额定无 datasheet）、`:149-152`（PC USB 必然塌压的定量）、`:162`（方案 A）、`:408`（T-09 待实测）；`risk-register.md:18`（R12，缓解含 470µF/外接 3.3V/改板需拍板）；`demo...edv11p.c:99-102,186,195-203,314-322`；`charter.md:40`（改板属范围外，需用户决策）
- **影响**：两种失败都发生在"30 分钟稳定性"这一步，且**现象相同**（偶发坏帧/轨迹跳变）：一种来自电源塌陷导致模组重启，一种来自背压丢字节。若不在上板前把两者分别变成可观测信号，Gate-2 会陷入"到底是谁的锅"的反复试错。
- **建议动作**：① 上板顺序固定为"先测电源（T-04 查 datasheet / T-08 浪涌 / T-09 双源 ORing）→ 再跑数据"，并将 T-09 从"demo 供电方案"这类低优先级描述提升为**上板前必做**；② 方案与代码二选一：把 `APP_EDK60_EDV11P_UART_RX_BUF` 提到 32768（≈356 ms，Kconfig 上限已允许）**或**把 `BR_USB_WR_RETRY` 收到 2 次（≈210 ms），并在注释里改掉"余量 8 倍"；③ 增加 UART 溢出/水位计数（`uart_get_buffered_data_len` 采样或驱动事件队列消费）并纳入 Gate-2 判据；④ 把"USB-C 只传数据"这句改成"USB-C 仍会带入 VBUS，必须实测 ORing 行为（T-09）"。
- **责任角色**：硬件工程师（电源三测）+ 嵌入式/软件工程师（缓冲/计数/注释）

#### P1-05 TX 引脚归属（H3-A = IO0 还是 IO5）未决，且失败模式是"只能收不能发"

- **问题**：`edk60_board.h` 同一文件内自相矛盾（`:142` "H3（A=IO0…）" vs `:148` "IO5（H3 的 A 脚）"）；`docs/EDK60-pinmap.md` 同样并存（`:41` 实测 IO5 收到应答 vs `:47`/`:255` A=IO0）。hw 文档已登记为 C-1 并要求万用表通断核实（`hw:106,300`），但该项被归入"待实测 12 项"而未成为**上板准入条件**。
- **证据（双向）**：
  - 支持 IO5：`docs/EDK60-pinmap.md:41`「模组 RX ← MCU TX = IO5（H3 的 A 脚）｜发 `get_version` 收到 `5A 07 80 "166" EC`」；`agents.md` §1 同表（作为最高优先级实测事实）。**这一条是功能级反证**：模组只有在收到命令时才会回 `166`，说明 MCU→模组通路确实通。
  - 支持 IO0：`docs/EDK60-pinmap.md:255`（H3 表 A 脚 = ADC1_0/IO0，串 10Ω）、`:264`、`edk60_board.h:142`。
  - 未决理由：那次 `get_version` 是否确实经由 H3 插座的 A 脚完成、中间是否换了转接/飞线，材料内没有记录；`pinmap` 把"H3 丝印 A R T 与 GPIO 的对应"单列为 H-05 未确认项（`:380`）。
- **影响等级判定**：**功能风险 低-中**（存在功能级反证，倾向 IO5 成立）；**但失败后果高**（若 TX 不通，上位机所有 GET/SET 失效 → 无 0x70 → 与"模组不支持人数统计"完全同症状，`analysis:588`）。因此它的真实危害不是"线路错"，而是"**把接线问题误诊成型号问题**"，进而触发错误的升级路径（去要 -02 模组）。
- **建议动作**：① 把 `hw:300`（清单 #6 通断核实）从"建议"提升为**首次上板前的硬门槛**（5 分钟成本）；② 上板时先用 §7.1 的只读帧 `GET 0x01/0x02/0x80`（`hw:421-428`）确认双通道，再谈 0x70；③ 记录"若无应答 → 先查 TX/SET 通路，不得直接归因型号"（`analysis:588` 已有该逻辑，需提升到 checklist 第一层）。
- **责任角色**：硬件工程师（通断 + 上板）+ 测试工程师（记录判读顺序）

#### P1-07 洁净判据的四个漏洞（"未归属字节率=0"不够）

红队视角逐层找"遗漏的写者"与"判据假阴性"，结论是：**机制判断正确，但"可证伪性"不足**。

- **漏洞 1｜判据双轨**：方案把"未归属字节率 = 0"定为洁净判据（`analysis:132-139`，退化/失败阈值 0.1%），但脚本的 **PASS 判定只含 4 项**（坏帧率、帧完整率、假同步率、msgid 跳号率，`edv11p_frame_check.py:103-108`），"无法解析字节"只作为 `warnings` 与打印项（`:123-126,1101`）。后果：**每 30 分钟可容许约 18 次重同步事件仍判 PASS**（0.1% × 18000 帧），而 R1 的验收口径是"未归属字节 = 0"。两个口径不一致时，Gate-2 会引用 PASS 那个。测试计划确实补了人工判据（`frame-check-test-plan.md:136` 第⑧项"unparsed 段数 = 0，若 > 0 必须完成污染反查"），但**工具自动结论覆盖不到，靠人读 warnings**。
- **漏洞 2｜"源码零 printf"没有任何自动门禁**：洁净性依赖三条人工约定（`analysis:116-125` C1~C4），其中 C4"新 demo 源文件内零 printf/ESP_LOGx"完全靠自觉。当前工程里 `edk60_board.c` 有 30+ 处 `printf`（`:70-110,133-148`），其中横幅首行 `printf("  EDK60 (ESP32-C6)  Demo 运行中\n")`（`edk60_board.c:72`）里 "ED" 两字节相邻 —— 方案说得对，这会制造假同步。它现在被 `sdkconfig.defaults.radar_bridge_edv11p:39-40` 关掉了，但**没有任何机制阻止**未来有人把横幅打开或往新 demo 里加一行 `ESP_LOGI`。建议：构建后用 `nm` 检查 app ELF 是否还有 `printf/vprintf/esp_log_write` 的引用（本 demo 应为 0），作为 T1-3 的一部分。
- **漏洞 3｜非 `build_all.ps1` 路径完全没有洁净强制**：`CONFIG_APP_EDK60_STARTUP_BANNER` 与 `PRINT_PINMAP` 的 Kconfig **默认是 y**（`main/Kconfig.projbuild:60-62,71-73`），只有 demo 专用 defaults 才关（`sdkconfig.defaults.radar_bridge_edv11p:39-40`），而该 defaults 只有在 `build_all.ps1` 或手工传 `SDKCONFIG_DEFAULTS` 时才生效（`build_all.ps1:175-183`）。第三方按 recipe 走 `idf.py menuconfig` 自编（G4 场景）时，会得到一个"日志全开 + 横幅以 ED 开头"的固件 —— **现象是"上位机一直坏帧"，而用户会怀疑硬件/接线**。这是 G4 复现性最可能的坑。
- **漏洞 4｜"零写者"清单不完整**：方案诚实列了 3 条残留源（`analysis:141-148`：panic、ROM putc、bootloader），但未提：① `esp_log_level_set("*")` 只能压 `esp_log_write` 路径，压不住任何 `printf`（源码里 C4 是唯一保障）；② 用户若自行关掉 `APP_EDK60_EDV11P_SILENT_LOGS`（Kconfig 默认 y，可关，`main/Kconfig.projbuild:682-684`），就只剩编译期 `LOG_DEFAULT_LEVEL_NONE` 一道保险，`ESP_EARLY_LOG*`/`printf` 都还在；③ 该 demo **从未构建**，因此"C1~C3 三个配置真的生效"目前**没有任何构建产物级证据**（`build-radar_bridge_edv11p` 为空）。

## 五、对争议点 A~F 的逐条裁定

### A. 型号分支冲突（-02 口头确认 vs 本地 hex 全为 -03）

**裁定：冲突必须在上板前"定性"、在上板后"定论"；允许以 `GET 0x02` 回读作为判定动作，但不得以回读"作为放行条件"预先放行。**

理由：
1. 现有一切证据都不足以判定型号：本地 6 个 hex 只能证明"本地无 -02 固件"（`hw:198-217`），不能证明"插在 H3 上的是 -03"；用户口头确认同样不是证据。正确表述是**型号未定**。
2. 该冲突不影响 P1（固件实现）与"能不能上板跑起来"：桥接层与分支无关（`analysis:396-403`）。
3. 但它**决定性影响 G2/G3 的可达性**（`charter.md:20-21`）：若为 -03，0x70 根本不存在（`hw:196`），且"不是软件能绕过去的"（`hw:265`）。因此它必须是 **Gate-2 的第一个判定动作**，且必须与"失败后怎么办"绑定，而不是一条"待回读确认"的备忘。
4. 现状最危险的不是"不知道"，而是**风险册已经被口头确认降级**（R11 P=1，`risk-register.md:17`），使这个"可能推翻整个 demo"的不确定性退出了必审清单。这属于证据门槛问题，必须回退。

**结论性处置**：允许放行进入 P1/P2；条件 C-1（型号判定卡 + R11 恢复 P≥3 + 三条分支处置预案）。若回读显示 -03/无 0x70 → **Gate-2 直接 NO-GO**，不得以"先发个 demo 再说"方式带病发布。

### B. 供电（自称头号风险）

**裁定：属于"研发可自行处理（查 datasheet + 实测 + 软件侧加固）"+"用户提供物资/授权改板"的混合事项；不构成 Gate-1 阻断，但构成 Gate-2 的硬门槛。**

理由：
1. 基线缓解方案 A+B 是**零改板**的（`hw:162-163`），因此不需要用户对"技术方案"拍板 —— 技术上研发可自行闭环（查 T-04、测 T-08/T-09、按需调缓冲）。
2. 但有两件事**超出研发权限**：① 物资（5V/≥2A 适配器、470 µF 电容）需要采购/用户提供；② 若 A+B 仍复位，方案 C/D 涉及焊接/改板，而章程明确"不修改 EDK60 硬件、不改板、不飞线（若供电实测不足，走'用户决策'）"（`charter.md:40`）→ **必须用户拍板**（决策项 2）。
3. 现状有一个必须纠正的认知错误：方案 A 的前提"USB-C 只传数据"物理上不成立（见 P1-04）。因此 T-09（双源 ORing 行为）必须提前到上板前，而不是排在 12 项待实测的中后段。
4. 另外：风险册把"固件 `PWR_READY_MS` 300→1000"当缓解措施（`risk-register.md:18`），但该参数在固件中**不存在**，代码反而是"刻意为零延时"（`:527-528`）。这一点必须更正，否则 R12 的闭环证据链是假的。

**结论性处置**：不阻断 Gate-1；条件 C-4（电源三测 + 缓冲复核）为 Gate-2 上板当天的**前置**动作，且必须先供电后数据。

### C. 斜装坐标系依据缺失

**裁定：影响等级 = 高（直接决定 G2 "轨迹与实际移动一致" 的成立性，同时污染 recipe/案例/网页标签三处对外内容）；`recipe` 中必须明确写明"侧装需要侧装版固件（或由上位机补偿），且本 demo 的坐标口径以实测为准"，且禁止把"固件已完成 XYZ 转换"写成已核实事实。**

理由：
1. 协议层确实没有任何倾角/旋转参数（`hw:271-274`），官方安装说明是水平 0°（`hw:271`）。这是**书面证据**。
2. 相反证据只有一行第三方脚本注释（`web:25`），强度远低于前者，却被写成"已核实"（`recipe-brief.md:58-69`）并固化为 DEC-02（`dispatch-log.md:18`）。
3. 这条争议**在 Gate-1 无法关闭**（需上板），所以不能作为阻断项；但它必须从"事实"降级为"待验证假设"，并配可判伪用例（P1-02 建议 ③）。
4. 关于"是否需在 recipe 里写明必须使用侧装版固件"：**必须写，但写法要改成条件句**——"若模组为 -02（人数统计）分支且固件为侧装版，则上位机不做旋转；否则需在 PC 侧补偿或改用 0x73"。直接写"必须使用侧装版固件"会让读者以为存在一个明确可订购的侧装 SKU，而目前材料并不支持这一点（`recipe-brief.md:19` 自己也把型号标为待定）。

### D. 控制台洁净路线（红队视角）

**裁定：路线唯一且机制正确，可冻结；但"未归属字节率 = 0"这一个判据不够，必须升级为"判据组合 + 自动门禁"。**

漏洞清单（详见 P1-07）：① 判据双轨——工具 PASS 不含"未归属字节"；② "源码零 printf"无自动门禁，而 BSP 横幅首行就以 `ED` 开头（`edk60_board.c:72`）；③ 非 `build_all.ps1` 构建路径下横幅/引脚表默认全开（`Kconfig.projbuild:60-62,71-73`），第三方自编必中招（G4 风险）；④ 写者清单未覆盖"运行时关掉 SILENT_LOGS"与"从未构建因此无产物级证据"；⑤ 唯一被工具补上的漏洞是"零帧真空通过"（`:740-744`），值得保留并要求在 Gate-2 引用。

补充一条**机制层**的红队结论：方案对"日志会插进帧中间"的物理机制论证（`analysis:66-82`，含 `usb_serial_jtag_vfs.c:148-171` 逐字符直写 + `'\n'` 触发 flush、secondary 模式不装驱动因此两个写者不互斥）是**本次材料中最扎实的一段**，我独立复核后同意其结论：只要还存在任何一字节 `printf`，就一定会产生"帧中插字节"的坏帧，而不只是"多一个假帧"。因此"过滤/无害化日志"这条路（方案候选⑥）确实物理上不成立。**这一段可以作为冻结论据。**

### E. 引脚文档冲突（H3-A = IO0 vs IO5；EN=IO14 vs IO15）

**裁定：实际风险等级 = 低-中（功能层低、诊断层中）。不构成 Gate-1 阻断，但通断核实必须成为首次上板的硬门槛。**

理由：
1. **EN=IO14 已有强证据**：拉高/拉低时丝印 RADAR 红灯同步亮灭、连续 5 次（`pinmap:42,95`；`edk60_board.h:132-135`），且静态断言锁死（`edk60_board.h:147-150`）。这条冲突实际上**已解决**，剩下的只是文档残留（P2-03）。
2. **H3-A 未定论**，但存在功能级反证：`get_version` 有应答（`pinmap:41`），说明 MCU→模组通路成立。若 H3-A 真是 IO0，则当前 `TX=IO5` 应完全无声 —— 与历史记录矛盾。
3. 之所以仍要通断核实：失败模式太"像"别的问题。TX 不通的症状是"只能收不能发"（`analysis:588`），与"模组不支持 0x70"（`hw:196`）在现象层完全同构，而两者处置南辕北辙（一个查线，一个换模组）。用一个 5 分钟的万用表动作换掉一次可能的错误升级，性价比极高。
4. 判定：不阻断 Gate-1；条件 C-5（通断核实，首次上板前）。

### F. 网页工具验证充分性（自测 5/5 + 21/21，无真实浏览器目检、无真机）

**裁定：当前状态足以支撑"P0 交付物（设计 + MVP + 模拟模式）"放行；不足以支撑"线上演示"承诺。**

理由：
1. 证据强度分级：帧解析与渲染管线是"逻辑级 + 桩环境级"验证（`release/track-selftest.md:10,15-31`），文档本身诚实标注了两项未覆盖（`web:398-399`）。对 P0 阶段这是**合适的**（Gate-1 的验收标准只要求"模拟模式可运行 + 用例通过 + 不做旋转"，`gate-1-scheme-freeze.md:20`）。
2. 但 G3（网页版可实时演示）与 G5（线上演示可用）是**对外承诺**（`charter.md:21,23`），其证据必须是"真实浏览器 + 真实设备 + 真实流量"。桩环境的 21/21 无法替代：Canvas 在真实 DPR 下的可读性、Web Serial 在 921600 下的分包行为、浏览器对 `navigator.serial` 授权弹窗的实际交互，都在桩环境之外。
3. 额外的、桩测试发现不了的证据缺口：U2（0x70 的 op 是否只 0xA3，`web:357`）、U3（z 是否离地高度，`:358`）、真机 SET 应答与 ACK（`web:399`），以及 **P1-06 的自动 SET 时序问题**（`track.html:1474-1498`）——这三类都只能在真机暴露。
4. 因此放行条件为 C-10：真实 Chromium 目检（按 `track-selftest.md:280-295` 清单）+ 真机联调 + 双端一致性（G-S4）+ 一次"干净人"走查；**在 C-10 完成前，禁止在 docs 站点/社媒/案例中出现"线上演示可用"或演示录屏作为已实现能力的证明**。

### 决策：`GO-with-conditions`

**判定依据（按 review-gate 口径逐条对表）**

| 口径 | 要求 | 本次情况 | 结论 |
|---|---|---|---|
| GO | 全部满足，无 P0/P1 | 有 7 条 P1 | ❌ |

| NO-GO | 存在 P0，或 P1 无缓解计划 | 无 P0 | ❌ |

**放行的实质内容**

1. ✅ 允许进入 P1：`radar_bridge_edv11p` 固件收尾（构建、`nm` 门禁、缓冲/计数加固）与 Kconfig/defaults 一致性修正。
2. ✅ 允许进入 P2：上板实测（前提是 C-1/C-4/C-5 三项上板前动作先做，见 §7）。
3. ✅ 允许启动 P3 文档写作的**骨架部分**（结构、字段、FAQ、避坑），但**事实性断言**（坐标口径、型号、供电要求、演示录屏）必须留占位，直到对应实测证据到位（`recipe-brief.md:103-110` 已给占位清单，做法正确，应严格执行）。
4. ❌ **不**允许对外发布任何"轨迹正确 / 线上演示可用 / 支持侧装 60°"的结论性表述（Gate-3 前禁止，且受 C-10 约束）。
5. ❌ **不**允许跳过 C-1（型号回读）就宣布"demo 打通"。

**为什么不是 NO-GO**：桥接主干的技术判断经我独立复核成立（控制台扇出机制、背压点、帧校验判据、双源供电路径都有可回溯证据），且所有 P1 都有在本阶段可执行的缓解动作，不存在"必须先解决才能开工"的阻断项。

**为什么不是 GO**：三处"结论强度超过证据强度"（P1-01 型号、P1-02 斜装、P1-04 供电前提）若原样带入上板，最可能的损失不是返工，而是**错误归因后的错误决策**（去要 -02 模组 / 去改板 / 去怀疑固件），这正是 Gate 要拦的东西。
