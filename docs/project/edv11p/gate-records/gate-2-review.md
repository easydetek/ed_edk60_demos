## 总体结论

**决策：GO-with-conditions（CA）**
**P0 = 0 ｜ P1 = 7 ｜ P2 = 10 ｜ 需用户拍板 = 5**

一句话理由：**固件"可用"已被多重直接证据证实**（我从产物侧复核：17 个 demo 的构建产物齐全、合并固件 SHA256 与发布记录逐字节一致、文档站与工程内 `track.html` 字节相同且含缺陷修复、启动横幅静态门禁 PASS、30 分钟捕获报告 PASS）；**但"可用"被材料写成了"完美"**——「帧完整率 100%」缺前提与对账、「轨迹正确」被替换为「轨迹可见」、目标 ID 与 `z` 语义被当作已验证结论写进了**已经上线**的对外页面。这些不阻断固件放行，但必须以 CA 条件在进入 Gate-3 前收紧，否则 Gate-3（对外发布收尾）会把超证据表述固化为对外承诺。

## 四、逐条回答 Gate-2 草稿的 6 个必答问题

> 对应 `gate-2-firmware-and-onboard.md` 第四节，逐条作答，不绕开。

### Q1 30 分钟 0 坏帧 0 重同步，是否足以支撑「帧完整率 100%」的对外表述？前提必须同时写出什么？

**答：不足以支撑无限定的"100%"，足以支撑"未观测到坏帧/重同步/非协议字节"。必须同时写出的前提有 6 项，其中 2 项目前完全没写。**

不适用的原因（三条，都是口径问题而不是数据问题）：
1. **该指标在"无坏帧"时恒为 100%**。工具定义 `P4 帧完整率 = 好帧/(好帧+坏帧+重同步)`（`edv11p_frame_check_20261022-100607.json` `artifacts.rules`）。本次坏帧 0、重同步 0 ⇒ 分子=分母 ⇒ `complete_rate=1.0` 是恒等式，**它不度量"雷达发出的帧有没有漏接"**。漏帧只能靠 msgid 连续性间接推断，而工具的 msgid 判定是**分组**口径：不分组时 58 次跳号（`msgid.overall.jump_rate=0.0037`），分组（`op=0xA3/type=0x70`）后为 0（`grouped_pass_ungrouped_fail=true`）。这一层目前只有 `case-edv11p-person-tracking.md:105` 写了，`test-report` / `recipe` 都没写。
2. **统计窗口从 T+10 s 起算，前 2,970 字节被排除，全部对外/内部材料都没说**。JSON：`unattributed.window_start_offset=2970`、`window_bytes=528002`、`total_bytes=530972`（530,972 − 2,970 = 528,002 ✓）。也就是说 `stats.md` 里"530,972 B / 15,483 帧 / 尾部 1 B"这套账**对不平**：2,971 B 不属于任何帧（2,970 段 + 1 B 尾）。读者按材料给的数字复算会得到 2,971 个未归属字节，而不是 1 个。
3. **"帧率 vs 设定值"没对账**：配置 `0x10=2`（100 ms ⇒ 名义 10 fps），实测 8.60 fps（`frame_rate=8.6017`，平均间隔 116.5 ms）。recipe 附录 C④ 已诚实登记"未归因"，但 `test-report-onboard.md` §二 又写了"219 帧/4.4 s"（≈49.8 fps）——**同一台设备出现 49.8 / 10 / 8.6 三个帧率**，材料里没有任何一处解释，这是复核者第一个会问的问题。

必须同时写出的前提（建议直接抄进 recipe 附录 A 与 flash.html）：
| # | 前提 | 当前状态 |
|---|---|---|
| ① | **采集脚本** `tools/capture_gate2.ps1`，且它**每 60 s 主动发 1 条 `GET 0x05` 保活**（共 29 次，对应 29 帧 `0xA2/0x05`）⇒ 本次**不是被动监听**，PC→雷达方向有注入 | ❌ 未写（recipe 第 39 行只写"每 60 s 一次保活 GET"，但没写"所以这不是纯监听"） |
| ② | **主机与链路**：COM8 / VID:PID `303A:1001` / 原生 USB CDC / Windows / 无流控 | ✅ 已写（recipe 附录 A） |
| ③ | **供电方式**（USB-C 供电？DC-005 + 适配器？）与实测余量 | ❌ 完全没写（`meta.txt` 只有 `start/port/seconds/file`；`test-report` §一 只列 COM8） |
| ④ | **时长** 1800 s、单次、单板、单模组、单场景 | ✅ 已写 |
| ⑤ | **warmup 10 s（排除 2,970 B）+ 末尾 1 B 截断** | ❌ 未写（recipe 第 837-838 行只解释了"为什么要跳过 10 s"，没给 2,970 B 这个数） |
| ⑥ | **场景真值**：在场人数、走位路线 | ❌ 完全没写 |

**建议对外句式（替代"帧完整率 100%"）**：
> 「1800 s 连续采集：`0xA3/0x70` 目标帧 **15,454** 帧，组内 msgid **连续无跳号**；坏帧 0、重同步 0；观测窗口自 T+10 s 起算（前 2,970 B 为上电/启动段，不计入），窗口内未归属字节 **1 B**（采集到点关串口的截断，非设备行为）。」

### Q2 未归属 1 字节如何表述才既准确又不吓人？是否需要改脚本后复测？

**答：现有三处表述已经合格（准确且不吓人），复测建议做但不应作为放行条件。**

- 合格点：`test-report-onboard.md` §五 WARN 说明、recipe 第 43-45 行、case 第 107 行都做到了"定位到字节 + 归因到采集动作 + 明确不是丢帧（坏帧 0/重同步 0）+ 给出改进办法"。case 第 107 行还额外给了"528,002 B 窗口中的 1 B，比率 1.9×10⁻⁶，属告警级"，这一句是三种写法里最准确的，建议**以此为准统一**（`test-report` 与 `recipe` 缺这几个数）。
- 是否需要复测：**建议做，但不作为 Gate-2/Gate-3 条件**。理由——要消掉它必须改脚本为"到点后读完当前帧再关口"，这会引入"末帧是否完整/是否会多读"的新判断，收益 1 字节、代价一次 30 分钟采集 + 一次脚本回归。更有效的动作是把工具补上 `--strict-gate`（unparsed>0 或时长<90% 直接非 0 退出，即 Gate-1 的 P2-05，目前 grep 无实现），让这个字节**在纪律上不可被忽略**，而不是物理上不存在。

### Q3 型号判定卡能否正式关闭？条件是什么（是否必须再取一次 `GET 0x02` 存档原始帧）？

**答：可以正式关闭。建议补一次整帧存档，但不必作为关闭前提。**

- 关闭理由（证据充分）：回读 `EDV11P_VA,V1.3.3,0x95F0` + 30 分钟 15,454 帧 `0x70` 且 `payload_errors=0`。按 Gate-1 判定卡（`gate-1-disposition.md` §四"能稳定输出 `op=0xA3/type=0x70` → -02 行为成立"）判据已满足。
- 关闭时应附两条限定（避免把个案推广成系列结论）：
  1. 结论是"**这台模组的这个固件分支**具备人数/轨迹能力"，不是"EDV11P 全系列都能"。`case:164` 与 `recipe:848` 已正确写成"以设备回读为准"，但 `release-package-notes.md` §2 的"模块型号"栏、以及 `risk-register.md` R11"人员定位侧装版成立"这类表述容易被读成系列结论。
  2. 存档目前只有 **23 B 载荷**十六进制，没有**整帧**（含 2 B 头 + 2 B 长度 + 2 B msgid + 校验）。而载荷首两字节正是 `45 44`——把它当"原始帧"贴进文档，会让读者以为帧头就在那里。建议再取一次 `GET 0x02`，保存**整帧 hex + `.bin` 片段 + 偏移**，作为结项交接证据（P2-02）。

### Q4 网页端只有 HTTP 200 + 模拟模式待目检，能否作为「线上演示已就绪」的证据？

**答：仅凭 HTTP 200 不能；但实际证据已经超过这条口径，G3 可判达成——只是"线上（主域名）"不成立。**

- HTTP 200 只证明"文件能取到"，不证明"能连串口、能出图"——这个区别在本项目里被一次真实缺陷印证了：`btn-connect` 永远置灰（`test-report-onboard.md` §七第 4 条），页面 200 一切正常，人一点就废。
- 实际已达成的证据：① 用户实机在本地 `8770` 完成"连接 → 出图"（`test-report` §六 T2-3）；② 缺陷修复已进产物（`track.html:2102`），且我复核 `release/edv11p/track.html` 与文档站 `static/edk60/edv11p/track.html` **字节一致**（92,027 B / `19C5EA60…8CB1`）⇒ 线上 GitHub Pages 上跑的就是修好的那份（`publish-notes.md` §9.2 记录 92,027 B 200）；③ 默认只读有自测断言（`:832-858`）。
- 因此口径应为：**"GitHub Pages 域名下网页演示可用（用户实机确认）"**；不能说"线上演示已上线"——`docs.easydetek.com` 仍是 404（`publish-notes.md` §9.3），主域名可用性属 Gate-3 的开项。

### Q5 17/17 回归尚未完成，是否构成 Gate-2 阻断？

**答：不构成阻断——因为"未完成"这个表述已经过期，但 G6 的验收物（汇总表）确实缺失。**

- 我从产物侧核对：17 个 demo 构建目录齐全，全部 mtime 落在 **2026-10-22 11:21–11:39**，每个目录都有 `edk60_demos.bin`（如 `radar_bridge_edv11p` 178,656 B、`hello_board` 178,704 B、`wifi_sta` 935,264 B）。这与"13 个一轮 + 4 个补跑、0 失败"的描述一致 ⇒ **回归事实上已完成**。
- 但章程 G6 的判定证据写死是"`build_all.ps1 -Size` **汇总表**"、判定人是评审官（`charter.md:24`）。现在没有任何归档文件可供引用，`firmware-implementation-notes.md` §6.3 仍是"待补"、`workflow-plan.md:28` 仍"进行中" ⇒ G6 状态是**"事实成立、证据未归档"**。
- 处置：列 CA 条件（C-4），要求把 `-Size` 输出落盘归档并在 Gate-2 记录中引用；不阻断，因为它不改变"能不能用"的结论，且复跑成本约 20–40 分钟。

### Q6 侧装几何标定（偏差 <30 cm）未做，是否必须作为 Gate-2 放行条件？

**答：不作为 Gate-2 阻断，但必须作为 CA 条件 + 对外表述红线，并在 Gate-3 前闭环或显式降级。**

- 为什么严格说它是 Gate-2 指标的一部分：charter G2/S3 写的是"**轨迹与实际移动一致**"（`charter.md:20,56`），而 Gate-2 草稿把它替换成了"轨迹与人数**可见**"，这属于**验收口径变更**，且没有变更记录。
- 为什么仍不建议阻断：Gate-2 的阶段目标是"固件可用 + 上板实测"，而标定失败只会改写"精度结论"，不会推翻"桥接通路零丢字节"这一核心结论；把它设为阻断项会把整条链路押在一次人工走位（约 20 分钟）上，性价比不成立。
- 因此裁定：① **对外表述先收紧**（不得暗示"轨迹精度已验证"）；② 标定作为 C-7，在 Gate-3 前完成，或把"轨迹正确"正式降级写进对外已知边界（case `:161` 与 recipe `:709` 已经这样写了，需要把 `:5`、`:68` 那两处更强的话收回）。

## 六、Gate 结论与理由

**决策：GO-with-conditions**

理由（按权重）：
1. **核心目标达成**：G1（30 分钟帧完整率 ≥99.9%）在**可复核的原始数据**上达成——`verdict=PASS`、坏帧 0、重同步 0、载荷异常 0、msgid 分组连续；G2/G3 的"可用"由用户实机确认，且我复核了产物一致性（网页缺陷修复确实在线上副本里）。
2. **无 P0**：零协议注入、控制台洁净、产物完整性三条主干我都独立核过，没有被推翻的地方。
3. **但 7 条 P1 全部是"结论强度 > 证据强度"或"证据未归档"**，且其中 3 条（P1-01/P1-05/P1-06）已经写进**已上线**的对外页面——这正是 Gate 要拦的东西。它们不需要改代码、不需要改硬件，只需要"改措辞 + 补一次采集 + 归档"，因此给 CA 而不是 NO-GO。
4. 与 Gate-1 的对照：Gate-1 的教训是"口头确认不能替代证据"；Gate-2 的教训是"**指标名称不能替代指标定义**"——"帧完整率 100%"这个说法本身没错，但它承载不了材料让它承载的结论。

**不允许在 CA 关闭前对外新增的表述（红线）**：
- ❌ "帧完整率 100%"（无限定）→ ✅ 改为 Q1 建议句式
- ❌ "6 个目标 ID 各自的轨迹可完整还原" → ✅ 改为"6 个 ID 均有轨迹数据；ID 可能被复用"
- ❌ "`z` 为离地高度/已实测离地高度" → ✅ 改为"`z`（设备高度轴）"
- ❌ "轨迹与实际移动一致 / 轨迹准确" → ✅ 改为"轨迹随人移动；几何精度未标定"
- ❌ "线上演示已上线" → ✅ 改为"GitHub Pages 域名可用；主域名待更新"
- ❌ "人数统计准确" → ✅ 改为"实测期间人数在 1~6 之间变化；无真值对照"

## 八、是否需要 Gate-3

**需要，且建议为"强制独立评审"，不是流程走形式。** 理由：

1. **对外内容已经上线，且当前存在 3 条超证据表述**（P1-01/P1-05/P1-06）。对外发布收尾正是 Gate-3 的把关对象（章程 S5/S6、`charter.md:58-59`）；在没有独立复核的情况下继续扩面（英文站、社媒、案例推广）会把措辞问题放成对外承诺。
2. **Gate-3 的验收项大部分尚未验**：S4「网页与桌面端轨迹一致」（同一时刻双端截图比对，评审官判定）没有证据；S5「Recipe 三步可复现」（第三方走查）未做；S6「文档站上线」只完成了 GitHub Pages 一半。
3. **发布运维有开项**：`docs.easydetek.com` 404（需用户在服务器执行 `git pull && docker compose up -d --build`）、CI `Sync to Gitee` 自 2026-10-18 持续失败（每次上线需手工绕过）——这两条不属于技术债，而是"对外可用性"事实，必须有人签字。
4. **本期特有的交接风险**：项目接近结项，而交付物索引、计划状态、发布记录三处数字已经与事实脱节（P2-01/P2-03/C-8）。Gate-3 应同时充当"结项交接包"的把关点，否则结项文档会继承这些错数值。

Gate-3 建议纳入的最小评审项：① CA 条件 C-1~C-9 的关闭证据；② `docs.easydetek.com` 两个 URL 的 200 记录；③ S4 双端一致性截图；④ Recipe 第三方走查记录（或明确降级）；⑤ 结项交接包的交付物索引/版本冻结。
