### 1.4 EN（雷达电源使能）极性与上电时序

| 项 | 值 | 证据 |
|---|---|---|
| 使能脚 | **IO14**（`EDK60_PIN_RADAR_PWR_EN`） | S1 L149 + L130–146 实测定论；S2 §二实测表；S11 |
| 极性 | **高有效**：`EDK60_RADAR_PWR_EN_ACTIVE_LEVEL = 1`（输出高 → U4 EN=1 → 3.3V_RADAR 上电） | S1 L150 |
| 默认状态 | **上电默认关闭**：U4.EN 经 R2 **10k 下拉到 GND**（不是上拉），复位后 EN=0，3.3V_RADAR 不输出 ⇒ **可热插拔模组** | S1 L90–101；S2 §二附「四条必须遵守的结论」#1 |
| 驱动方式 | 推挽输出即可（10k 下拉只需 0.33 mA）；需回读电平的场合用 `GPIO_MODE_INPUT_OUTPUT` | S1 L100；S3 C1 |
| 目视校验 | 丝印 **`RADAR`** 红灯（LED5）挂在 3.3V_RADAR 轨上 → **红灯亮 = 雷达已上电**；丝印 **`L`** 橙灯（LED4）由 **IO15** 驱动，**与电源无关**（不要用它判断电源） | S1 L46–48、L152–154；S2 §一；S11（IO15 拉高橙灯亮但红灯灭） |
| 关断/软复位 | EN 拉低 → 等 **≥300 ms**（确保模组供电落到阈值以下）→ 再拉高 | S2 §二附「上电时序建议」 |

**上电时序要求（EN↑ → 可通信）**：

```
① MCU 先上电并完成启动（3.3V 主轨 + USB 枚举稳定）
      ↓  （不要与 MCU 启动浪涌叠加，见 §2.3）
② IO14 输出高  → U4.EN=1 → 3.3V_RADAR 建立（丝印 RADAR 红灯亮）
      ↓  LDO 软启动 + 输出电容充电：精确上升时间 `待实测确认`（H-04 未关闭）
③ 模组内部上电复位/初始化（自检、射频校准）
      ↓  时长 `待实测确认`。参考值：同架构 EDV151 实测上电到 `radar_ready` 约 1 s
         （S10 代码 L801 注释「等模组初始化（上电到 radar_ready 约 1 秒）」）
④ 模组开始主动上报（EDV11P 为 0x45 0x44 帧；-03 默认工作模式 3=跌倒检测）
```

**结论**：固件当前 `CONFIG_APP_EDK60_BRIDGE2_PWR_READY_MS = 300 ms`（S10）**偏激进**，建议上板时先设 **1000 ms**，稳定后再逐步缩短。→ 列入待实测项 **T-02**。

### 2.3 定量核算

**稳态（平均 190 mA）**
- U4 耗散 = (5.0 − 3.3) V × 0.19 A = **0.32 W**
- 按 SO-8EP 类封装 θja ≈ 50 °C/W 估：ΔT ≈ **16 °C**，环境 40 °C 时 Tj ≈ 56 °C → **稳态无热问题**。

**启动浪涌（峰值 1200 mA）**
- 瞬时耗散 = 1.7 V × 1.2 A = **2.04 W**
- 若浪涌持续 < 10 ms，瞬态热阻 Zth 远小于 θja（量级 1 °C/W），**结温几乎不升（ΔT ~2 °C）⇒ 热不是主要矛盾**；
- **真正的矛盾是「电流能力」与「输入源能力」**：
  1. **LDO 限流**：若 AP7362 额定/限流点为 1.0 A，则 1.2 A 浪涌会被限流 → 3.3V_RADAR 塌陷 → 模组欠压复位循环。若额定 1.5 A，则余量仅 25%。**额定值 `待确认`（T-04），这是必须最先查的一条 datasheet 参数。**
  2. **5V 输入源塌陷**：3.3V/1.2 A 折算到 5V 侧约 **1.2 A**（LDO 输入电流≈输出电流）；加上 MCU 在 Wi-Fi 突发时约 0.3–0.35 A（3.3 V 侧），5V 侧总计 **≈1.5–1.6 A**。
     - 接 **PC 的 USB 口**（500/900 mA）→ **必然塌压**，且塌的是整条 5V 轨 → U3 输出也塌 → **MCU 一起复位**（这会把现象伪装成「板子坏了」）。
     - 接 **2 A 以上适配器**（DC-005 或 USB-C PD/2A 源）→ 有余量。

**结论（回答「启动浪涌是否会引起复位」）**：
> **会，且路径明确**：最可能的失败模式是「5V 轨被 USB 端口限流拉塌 → 主 3.3V 跟着塌 → C6 掉电复位」，而不是模组自己扛不住。
> 只要**用 DC-005 座 + ≥5V/2A 适配器供电**，并把「模组使能」放在 MCU 启动完成之后，风险就降到可接受。

命名规则（S6 slide 3 / S5 §2）：`ED`+`V`(60G)+`1`(雷达模组)+`1`(旗舰系列)+`P`(产品序号)+`-N`(无光敏)+`-03`(子产品序号)。**末两位就是产品分支。**

**手上的模组 = `EDV11P-N-03`，是「跌倒检测 & 人存」分支，不是人数统计分支。**

### 3.2 协议层面的硬约束

`EDV11P串口通用协议.md`（V1.9，S7）类型表原文标注：

| type | 命令 | 原文标注 |
|---|---|---|
| **0x70** | 追踪/人数目标上报 | **（仅人数统计产品支持）**；结构：感应区号、目标数、每目标 ID + x/y/z（int16, cm） |
| 0x72 | 跌倒上报 | （仅跌倒产品支持）；有人/无人 + 跌倒状态 0/1/2 |
| **0x73** | 跌倒目标上报 | **（仅支持跌倒-松下版本产品）**；目标 ID + 状态 + **x/y 坐标** |

⇒ **0x70（本项目要的人数统计/轨迹跟踪帧）不在 -03 的能力范围内。** 这不是版本高低问题，是产品分支问题。

### 3.3 现有 hex 全部是 -03 跌倒版（本次实测解析）

用 Intel-HEX 解析 + 可打印字符串提取（S9），结果：

| 文件 | 地址范围 | 镜像大小 | 内含版本/标识串 | 算法特征串（判定分支） |
|---|---|---|---|---|
| `EDV11P_N_03V116.hex` | 0x002000–0x016EE0 | 83.7 KB | — | 跌倒 |
| `EDV11P_N_03V118.hex` | 0x002000–0x0170A8 | 84.2 KB | — | 跌倒 |
| `EDV11P_N_03V119.hex` | 0x002000–0x017000 | 84.0 KB | — | 跌倒 |
| `EDV11P_N_03V120(1).hex` | 0x002000–0x016E44 | 83.6 KB | — | 跌倒 |
| `EDV11P_N_03_V121_SX-带人员定位的.hex` | 0x002000–0x014550 | 73.3 KB | **`V121SX1`**、`EDV11P_VA` | 跌倒（`Fallen` / `falldown maybe` / `Standup Judge` / `Fall[%d]: Min_Z=` / `Get up`）+ 目标追踪内部量（`NewTarget Gen X_Cen=`） |
| `EDV11P_N_03_V123_SX.hex` | 0x002000–0x014964 | 74.3 KB | **`V123SX1`**、`EDV11P_VA` | 同上（跌倒） |
| `11P_N_03_V123_SX_All.hez.hex` | **0x000000**–0x014964 | 82.3 KB | `V123SX1` 同类 | 同上；**从 0x0 起 ⇒ 含 bootloader 区（全量镜像）** |
| `bootloader(1).hex`（EDV25P 目录） | 0x000000–0x0015D4 | 5.5 KB | — | bootloader 单独镜像 |

判读要点：
1. **文件名与内容都带 `_03`**，且全部包含跌倒判据字符串，**没有任何一个含人数统计分支标识**；
2. `_SX` = **松下版**（对应协议 0x73「仅支持跌倒-松下版本产品」）→ V121_SX / V123_SX 是「跌倒 + 松下目标坐标（x/y）」，**这是最接近「轨迹」的现有能力，但它不是 0x70 人数统计**；
3. `_All` 版从 **0x000000** 起 = 含 bootloader 的全量镜像（可用于救砖/首刷）；其余从 **0x002000** 起 = 仅应用（快速升级）；
4. 全部固件内**均无 `EDV11P-N-02` 分支**。

### 3.4 推荐烧录版本 + 回读验证

**情形 ①（本项目原始目标：人数统计/轨迹跟踪 0x70）**

> **推荐：不烧现有任何 hex。**
> 现网 6 个 hex 都是 -03 跌倒分支，刷哪个都拿不到 `0x70`。
> **升级路径（必须动作）**：向**雷达固件负责人**索取 **EDV11P-N-02（人数统计/轨迹跟踪）的模组 + 固件**。
> 内部对接人：**雷达固件负责人**（依据协议文档修订记录作者栏 S7，涉及 V1.0/V1.3/V1.7 多次修订；发布说明 V0.0.1 编制亦由其署名，S6 slide 2）。
> 需索取的三件套：① -02 模组实物 ② 对应版本 hex（连 bootloader 信息）③ 与固件匹配的协议文档版本（现有文档停在 V1.9/2026-07-14）。

**情形 ②（接受用现有 -03 模组，做「目标坐标 + 人存 + 跌倒」demo 作为过渡）**

> **推荐烧录：`11P_N_03_V123_SX_All.hez.hex`**（全量，0x000000 起，含 bootloader，2026-08-24，最新）
> 备选：`EDV11P_N_03_V123_SX.hex`（仅应用，0x002000 起，用于已能正常启动的板子快速升级）
> 被淘汰：V116 / V118 / V119 / V120（无 SX，无 0x73 目标坐标）；V121_SX（比 V123 旧）

理由（逐条可查）：
- **最新发布**：2026-08-24（V116/V118/V119 为 5–6 月，V121 为 7 月）；
- **SX = 松下版**，是唯一被协议明确支持 `0x73 跌倒目标上报（含 x/y 坐标）` 的分支 → 能做「目标 ID + 坐标」的轨迹雏形；
- **`_All` 从 0x0 起**，带 bootloader，首刷/救砖一次到位，不必猜板子上 bootloader 版本；
- 能力边界要说清：**它给的是「跌倒+人存+目标坐标」，不是「人数统计」** —— 目标数上限、感应区（0x25/0x26）语义都受 -03 分支限制。

**烧录方式（S9 附带的 `EDV11P JLINK烧录说明.docx`，已解包读取）**：
1. 装 J-Link 驱动 → 打开 `JFLASH.exe`；
2. 载入 `JLINK` 目录下的 **`EDV11P.jflash`** 工程 → 选目标 hex → OK；
3. 用 **2.0 mm 顶针**接 `GND / 3V3 / TMS / TCK`（对应 J-Link 的 `GND / VCC / TMS(SWDIO) / TCK(SWCLK)`）；
4. 连好设备后按 **F7**（或 Production programmer）烧录。
> ⚠ 顶针烧录时**不要同时把模组插在 H3 上**（3V3 会与板载 3.3V_RADAR 顶牛）→ 见 §4 清单前置条件。

**回读验证（烧完必做，两条互补）**

| 目的 | 发送帧（hex，msg id = 0x0001） | 说明 |
|---|---|---|
| **读模块信息（主验证）** | `45 44 00 0B 00 01 A0 02 00 00 37` | GET type 0x02。应答 `45 44 00 22 00 01 A2 02 00 17 <value> <cs>`；value = `"EDV11P_VB"`(9B) + `,` + **固件版本(6B)** + `,` + **软件ID(6B)** |
| 读产品信息（辅） | `45 44 00 0B 00 01 A0 01 00 00 36` | GET type 0x01；value = 协议版本(1B) + 厂商ID(2B, 默认 `"ED"`) 。协议版本 0 + `ED` → 这条链路通了 |
| 读从机软件ID（辅） | `45 44 00 0B 00 01 A0 80 00 00 B5` | GET type 0x80；默认 `0xFFFF`。此帧与协议文档示例**完全一致**，可当「帧格式正确性」的基准 |

**判读标准**：
- `value[0..8]` = ASCII `EDV11P_VB` → 说明链路 + 波特率 + 帧格式全对；
- `value[10..15]`（6 字节 ASCII）**应形如 `V123S?`**（固件内版本串为 `V123SX1`）→ **实际回读字符串 `待实测确认`（T-06）**，因为 0x02 只有 6 字节，`V123SX1` 是 7 字符，截断方式未知；
- `value[17..22]` = 软件 ID（OTA 用），V123 对应的具体值 `待实测确认`；
- 若**完全无应答**：先查 EN/红灯/接线（§4 三层排查），再查波特率；若**应答 CS 错**：用 §1.5 C-4 的口径现算校验和。

> 校验和公式（S7 定义 + S8 实现一致）：`CS = (前面所有字节之和) mod 256`。
> 示例：`0x45+0x44+0x00+0x0B+0x00+0x01+0xA0+0x02+0x00+0x00 = 311 = 0x137 → 0x37`。

**若版本不支持 0x70 怎么办**：见情形 ①，找雷达固件负责人换 -02 分支。这条**不是软件能绕过去的**。

### 3.5 斜装（侧装）能力评估

| 项 | 现状 | 证据 |
|---|---|---|
| 官方安装方式 | 「**雷达发射面朝下，模组水平安装于顶部**」；安装倾角标注 **0°（水平）**；「安装对判断效果影响极大」；「尽量确保安装后雷达平面与地面水平」 | S6 slide 12 / slide 7；S5 §3.1 Installation Guide |
| 挂高 | 可配 0–400 cm，默认 300；文档给出 3.0 m→半径 2.5 m、2.5 m→1.8 m 的经验关系 | S5 Tab.1.3 / §3.1；S6 slide 12 |
| 可配的「几何」参数 | 只有 **0x20 检测范围（x/y 矩形）**、**0x21 检测高度（min/max）**、**0x22 挂高** —— 全部是**俯视正交坐标系**参数 | S7 类型表 |
| **倾角/坐标系旋转参数** | **协议中不存在**（0x20–0x33 全部枚举过，无 tilt / rotation / mount angle 类命令） | S7 + S8 `edv11p_type_t` 枚举 |
| 外壳要求 | 「必须避免金属或金属镀层」，「推荐塑料/树脂等雷达透波材料」 | S5 §3.1 |

**结论**：
> 本项目「绕 +y 倾斜 60°、主坐标轴俯角 30°」的侧装方案，**在 -03 的协议与文档中没有任何支持声明**，也**没有倾角补偿参数**。
> 也就是说：模组输出的 x/y/z 是**它自己假定的水平俯视坐标系**下的坐标；侧装后 z 轴语义偏移、x/y 需要外部做旋转矩阵换算，**且算法本身的检测高度门限（0x21）是按水平吊装标定的**。
> 因此：**「-03 支持侧装坐标系」无书面依据 → `待实测确认`（T-07）**。
> 需要固件侧确认的问题清单（一并问雷达固件负责人）：① -02（人数统计）分支是否有倾角/侧装参数？② 侧装时 0x21 检测高度按「垂直离地高度」还是「沿波束距离」解释？③ 盘头的 60°/30° 是否需要固件按旋转矩阵换算，还是要求 x/y 直接输出？

### 3.6 必须提醒固件侧的一点（本条影响上板成功率）

`demo_get_started_radar_bridge.c` L777–822 在启动时会**向模组串口依次下发 6 条 EDV151 专用命令**（`0x5A ...` 帧：`turn_on` / `set_time` / `set_para` / `set_gain` / `set_boost`），且当前 `CONFIG_APP_EDK60_BRIDGE2_TX_PIN = 5 ≥ 0` ⇒ `BRIDGE_HAS_RADAR_TX = 1` ⇒ **这段代码会被编译并执行**（S10 L146–150、L777）。

EDV11P 的帧头是 `0x45 0x44`，收到 `0x5A ...` 属于非法帧。**建议上板前把 `CONFIG_APP_EDK60_BRIDGE2_TX_PIN` 临时设为 `-1`（纯接收透传）**，或把该握手段替换为 EDV11P 的 `0x4544` 帧（见 §4.4 配置帧速查）。否则日志里会出现 6 行「握手 … (未取到 ok)」，容易误判成接线错。

## 4. 上板核对清单（可逐条打勾）

### 4.1 插模组前（板子空载）

- [ ] **1. 供电方式确认**：DC-005（J1）接 **5V/≥2A** 适配器；USB-C 接 PC 仅作数据。**不要**只靠 PC USB 口供电（§2.3）
- [ ] **2. 板子自检**：上电后丝印 `ON` 绿灯常亮；用 `hello_board` demo 确认串口有 banner
- [ ] **3. 雷达默认状态**：上电后丝印 **`RADAR` 红灯应灭**（EN=IO14 经 10k 下拉，默认关闭）。若红灯常亮 → 立即断电排查（说明 EN 被误拉高或 R2 异常）
- [ ] **4. 橙灯 `L` 含义**：橙灯由 IO15 驱动，**只反映 IO15 电平，不反映雷达电源**。不要用它判断供电
- [ ] **5. 量 H3 静态电平**（万用表，EN 关闭状态）：`P`/`V` 应为 **0 V**；`G` 与板 GND 通断应为 0 Ω
- [ ] **6. 通断核实 `H3-A` → `IO5`**（关掉 CONFIG C-1 冲突的关键一步，T-03）：万用表一端点 H3 的 `A`，另一端点 C6 的 IO5 焊盘/排针；同时确认 `H3-T` → **IO4**。**若 `A` 只到 IO0** → 停止，先解决接线再上板
- [ ] **7. 量 `H3-RES` 归属**：确认 `H3-RES` 是否与 C6 RESET 同网络（若同网络，模组侧绝不能驱动它，风险 R4）
- [ ] **8. 顶针/J-Link 是否已拆**：若刚烧过模组固件，**先拔掉 2mm 顶针/烧录治具**，避免 3V3 与板载 3.3V_RADAR 互顶

### 4.2 插模组（唯一正确方向）

- [ ] **9. 认丝印方向**：H3 丝印为 **`RES A R T G V P`**（H4 是 **`RES P V G T R A`**，**顺序相反**）。**必须插 H3，禁止插 H4** —— H4 的 `T` 与 EN 同网络，插 H4 会造成电源与数据互扰（S1 L141–146、S3 G2）
- [ ] **10. 对位**：模组 `VCC` 对 `P`/`V`；`GND` 对 `G`；`TX` 对 `T`；`RX` 对 `A`
- [ ] **11. 反接自检**：**VCC 与 GND 一旦对调 = 上电即烧模组**。插入前用万用表确认模组 `VCC` 焊盘与 `H3-P` 同侧、`GND` 与 `H3-G` 同侧
- [ ] **12. 插入力度/接触**：2.0 mm 排针+顶针，插到底、不歪、不半插（半插 = 丢帧，风险 R5）

### 4.3 上电后（按顺序看现象）

- [ ] **13. 红灯 `RADAR` 亮** = 3.3V_RADAR 已使能（这是唯一可信的供电目视判据）
- [ ] **14. 用万用表量 `H3-P`/`V` 对 `G`**：应为 **3.3 V ±5%**；若跌到 2.x V 或抖动 → 供电不足（§2.4 方案 C/D）
- [ ] **15. 万用表量 `H3-T`（IO4）静态电平**：模组未上报时通常是 **3.3 V 空闲高**（UART idle high）。若恒 0 V → 模组没起来或线断
- [ ] **16. 串口看数据**：921600 8N1，期望看到 `45 44` 开头的帧；-03 默认上报 `0x72`（跌倒/人存）或 `0x73`（SX 版目标坐标），而不是 `0x70`
- [ ] **17. 无数据时三层排查**（照此顺序，覆盖 95% 现场问题）：
  1. **电源层**：红灯亮不亮 → 不亮查 IO14 / EN / 适配器电流能力
  2. **通信层**：有没有任何 `45 44` 帧 → 没有则查 TX/RX 交叉、H3/H4、波特率 921600
  3. **能力层**：有帧但没有 `0x70` → 这是**产品分支问题**（§3.2），不是接线问题
- [ ] **18. 回读验证**：按 §3.4 发 GET `0x02`，确认 `value[0..8] = "EDV11P_VB"` 与固件版本串
- [ ] **19. 复位后行为**：按 SW1 RESET → 模组应随之断电重启（EN 回到下拉），重启后需重新等 ≥1000 ms 才有数据。若复位后一直没数据 → 检查 `PWR_READY_MS`

### 4.4 斜装场景建议初始参数（PM 要求的「必配项初始值」）

依据 S5「必配项」：自动学习或手动安装高度、检测高度范围、检测水平区域、状态上报周期、运动灵敏度。
**下列为「先跑起来」的保守初值，收敛靠实测（T-07 / T-11）**：

| 参数 | type | 建议初值 | 帧（msg id=0x0001，CS 已现算） | 依据/理由 |
|---|---|---|---|---|
| 挂高 | 0x22 | **200 cm**（=0x00C8） | `45 44 00 0D 00 01 A1 22 00 02 00 C8 24` | 本项目安装方案给定 200 cm |
| 上报周期 | 0x10 | **100 ms**（=0x0002，即 2×50ms） | `45 44 00 0D 00 01 A1 10 00 02 00 02 4C` | 轨迹跟踪要连贯，1 s 太稀 |
| 检测范围 | 0x20 | **先放宽**：X[-250,250] Y[-250,250]（=0xFF06/0x00FA） | 见下方长帧 | 侧装无依据，先宽后收；不要一上来按顶装半径收紧 |
| 检测高度 | 0x21 | **保留默认 50 / 250 cm** | `45 44 00 0F 00 01 A1 21 00 04 00 32 00 FA 8B` | 侧装语义未确认（T-07），先不动 |
| 运动灵敏度 | 0x23 | **7**（0x07） | `45 44 00 0C 00 01 A1 23 00 01 07 62` | 发布说明 CASE 1（高反射/小空间）推荐 7；场大再升到 10 |
| 存在灵敏度 | 0x24 | 先用默认 | — | 同上 |
| TX 功率 | 0x40 | **2（14 dBm）**，默认 4（16 dBm） | `45 44 00 0C 00 01 A1 40 00 01 02 7A` | 侧装距离近、易过饱和；发布说明建议降到 1–3（**仅 -03 支持该命令**） |
| 工作模式 | 0x05 | **1（追踪/人数统计）** —— 仅 -02 有效；-03 应为 **3（跌倒）** | `45 44 00 0C 00 01 A1 05 00 01 01 3E`（模式 1） / `45 44 00 0C 00 01 A1 05 00 01 03 40`（模式 3） | S7 工作模式定义 |

检测范围长帧（X[-250,250] Y[-250,250]，8 字节 value = `FF 06 00 FA FF 06 00 FA`）：
`45 44 00 13 00 01 A1 20 00 08 FF 06 00 FA FF 06 00 FA 64`
（CS 已复算：sum = 1380 → 1380 mod 256 = **0x64**）

> ✅ **本节所有帧的 LEN 字段与校验和已逐帧复算通过**（LEN = 实际字节数；CS = 前面所有字节之和 mod 256）。仍建议在脚本里用同一公式再算一遍，避免手抄错。实测中若 `SET` 收不到 `0xA2` 应答，先退回用 `GET` 类命令确认通道。

> ⚠ 上表 CS 我按公式算过一遍，但**任何一条下发失败前都不要反复重试**：EDV11P 是异步 Report 应答（op 0xA2），超时 2500 ms、重试 3 次（S8 `EDV11P_PRO_TIMEOUT_MS/RETRY_TIMES`）。建议先用 `GET` 类命令（0x01/0x02/0x80）确认通道，再发 `SET`。

### 7.2 写入（先读通再写）

见 §4.4 表。全部 `SET` 用 op `0xA1`，应答为 op `0xA2` + 同 type + 回显 value。

### 7.3 帧结构速查（S7 + S8 交叉核对）

```
+------+--------+--------+-----+------+--------+---------+------+
| 0x45 | 0x44 | LEN(2) | MSGID(2) | OP(1) | TYPE(1) | TLEN(2) | VALUE(N) | CS(1) |
+------+--------+--------+-----+------+--------+---------+------+
LEN = 整包字节数 = 11 + N（S8: total_len = 11 + value_len）
OP  = 0xA0 Get / 0xA1 Set / 0xA2 Report(被动应答) / 0xA3 Status(主动上报) / 0xA4 透传 / 0xA9 ACK
CS  = sum(前面所有字节) % 256
字节序 = 大端
```

- `0x00` 段 = 雷达主动上报；`0xA2` 段 = 对 Get/Set 的应答
- 上报为**异步**：Set 之后**必须等 Report 回来**再发下一条（S7「命令字」/ S8 超时 2500 ms、重试 3 次）
