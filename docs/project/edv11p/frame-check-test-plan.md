## 一、测试目的

固件侧**不做任何解析**，只把雷达字节流从 UART 搬到 USB。因此「桥接是否诚实」只能由 PC 侧客观统计证明。
本测试要回答三个问题：

1. **有没有丢字节 / 丢帧？** → 坏帧率、帧完整率、假同步（重同步）次数。
2. **有没有把帧搞乱？** → 每帧的长度/TLV/校验是否自洽，0x70 载荷能否正确解出 zone 与目标。
3. **有没有别的东西混进数据流？** → `unparsed_*.bin` 里的非协议字节是什么（重点：固件日志）。

**注意分工**：本工具证明的是「桥接链路」的完整性；上位机轨迹渲染是否正确由桌面端/网页端用例（Gate-3）负责，两者不可互相替代。

## 二、判定阈值与来源

### 2.1 阈值表（P0 前提 + 六条硬判据；脚本内 `THRESHOLDS` 常量，`--help` 与报告同源输出）

| 优先级 | 指标 | 计算口径 | 阈值 | 失败含义 |
|---|---|---|---|---|
| **P0** | 有效帧数 | 合法帧计数 | ≥ 1 | 整段一帧都没解出来 → 采集无效，其余判据 SKIP |
| **P1** | **未归属字节率** | (窗口内收字节 − 窗口内合法帧字节) / 窗口内收字节；窗口从 **T+10 s** 起算（`--warmup` 可调），跳过上电 bootloader 文本 | **= 0 → PASS**；0 < x < 0.1% → **WARN**；≥ 0.1% → **FAIL** | 数据流里混进了不属于任何合法帧的字节（坏帧/日志/误码） |
| **P2** | 重同步绝对次数 | 重同步事件计数 | ≤ max(1, round(3 × 时长/1800 s))，**30 分钟 = 3 次** | 有字符在「持续」插入流里；比率能摊薄少量异常，绝对次数不能 |
| **P3** | 坏帧率 | 坏帧数 /（好帧数 + 坏帧数） | < 0.1% | 帧被传坏（校验/长度/TLV/截断） |
| **P4** | 帧完整率 | 好帧数 /（好帧数 + 坏帧数 + 重同步） | **≥ 99.9%** | Gate-2 主指标不达标 |
| **P5** | 假同步丢帧估算率 | 重同步次数 /（好帧数 + 重同步次数） | < 0.1% | 流里出现非法字节，每次重同步至少丢 1 帧 |
| **P6** | msgid 跳号率 | 跳号次数 / 组内帧数（按 (op,type) 分组取最大组） | < 0.1% | 帧序中断 → 疑似丢帧（分组后仍超标才算） |

另有**静态门禁**（不需要硬件，与上面六条并行，见 T-FC-10）：

| 门禁 | 判据 | 失败含义 |
|---|---|---|
| 横幅门禁 `--check-banner` | 任何会写到数据串口的文案里出现相邻字节 **45 44**（ASCII `"ED"`）→ FAIL | 45 44 就是帧头，解析器会立刻假同步（后面的 `K6`=0x4B36 被当长度） |
| 源码零输出 | 桥接 demo 里出现 `printf` / `ESP_LOGx` / `puts` → FAIL | 固件自己在往数据流写字 |
| 日志路径 | 日志级别未关 **且** 第二控制台在 USB → FAIL | 日志会直接混进二进制流 |

上表 7 项（P0–P6）全部通过、且横幅门禁 PASS，才是 **PASS**；任一 FAIL 即 **FAIL**。样本不足判 **N/A**（不阻断，但要在 Gate 记录里说明原因），**WARN 不阻断但必须逐条记录**。

坏帧四分类（分别计数，报告逐项列出）：长度非法（<11 或 >4096）、校验和错误、TLV 长度与帧长不符、截断帧（流结束时字节不足）。这四类的字节**都算「未归属」**。

### 2.1.1 判据之间的优先级与冲突处理（评审 P1-07 要求写清）

1. **P0 先短路**：无有效帧时其余判据一律 `SKIP`，结论 FAIL —— 不能因为「没测到」而判通过。
2. **P1 是最严的洁净判据**，比 P5 严：
   * P1 按**字节**精确归属（窗口内每个字节要么属于某个合法帧，要么算未归属）；
   * P5 按**事件**估算（每次重同步 ≈ 至少丢 1 帧）；
   * 冲突时**以 P1 为准**。未归属字节 > 0 ⇒ P5 必然 > 0；反之 P5 = 0 而 P1 > 0，说明字节被插在「帧边界对齐处」——构不成重同步事件，但依然污染流，仍判 FAIL。
3. **P1 与 P3 不重复计分**：坏帧字节本身就算未归属，所以 P3 > 0 必然 P1 > 0。判定顺序是 P1 先判，P3 只用来说明「坏在哪一类」，两者不会互相掩盖。
4. **P2 与 P5 冲突时以 P2 为准**：短采集或高帧率下，几次重同步能把比率摊到 0.1% 以下（旧版工具最长可容约 18 次），但绝对次数 3 次/30 分钟照样越界 → FAIL。
5. **P4 与 P1 的关系**：P4 是章程 G1 的原始口径（含重同步折算），P1 更严（必须等于 0）。Gate 引用时要求 **P1 与 P4 同时满足**。
6. **WARN 的处理**：`0 < 未归属率 < 0.1%` 记 WARN —— 不改变 PASS，但 Gate 记录里必须写清「未归属字节数 + 来源（哪个 unparsed 段 / 哪一类坏帧）」，并纳入下一步归零计划。
7. **横幅门禁是准入检查**：它 FAIL 说明构建里存在会造假的文案；此时即使 30 分钟跑出 PASS 也不可信（只是碰巧没走到那段代码）。顺序上**先过横幅门禁，再跑 T-FC-01**。

### 2.2 阈值来源说明（为什么是这几个数）

| 阈值 | 来源 | 说明 |
|---|---|---|
| 99.9% 帧完整率（P4） | **项目章程 G1 / 成功标准 S3**（`docs/project/edv11p/charter.md`） | 客户可接受的演示级可靠性。按 10 帧/s × 1800 s ≈ **18000 帧**，0.1% ≈ **18 帧**的容错额度，落在「肉眼无感、轨迹不断线」的量级 |
| 未归属字节率 = 0（P1） | **风险 R1 的验收口径**（评审官 P1-07 要求与 R1 统一） | 纯字节透传桥接「一个多余字节都不该有」。R1 管「字节别掺」，G1 管「帧别丢」，是双轨：先用 P1 按 R1 判，再用 P4 按 G1 复核 |
| WARN 窄带 0~0.1%（P1） | 与 P3/P5 同量纲 | 留一个「可解释但不许重复」的窄带：偶发 1~2 字节误码不至于让整场 30 分钟白跑，但必须点名来源 |
| 重同步 ≤ 3 次/30 min（P2） | 由 R1 派生 + 实测经验 | R1 零容忍 ⇒ 理论上应为 0；给 3 次是承认「USB 侧偶发一次读边界错位」，再往上就说明有东西在持续插入 |
| 0.1% 坏帧率（P3） | 与 P4 同源（同一份数据的另一切面） | P3 只衡量「帧被传坏」（分母 = 好帧 + 坏帧）；P4 还把重同步计进分母。两者同时看可区分「帧传坏」与「字节被插入/丢失」 |
| 0.1% 假同步（P5） | 由 G1 派生 | 纯透传桥接不应产生任何非法字节；留 0.1% 只为容纳偶发 USB 缓冲毛刺，不是许可证 |
| 0.1% msgid 跳号（P6） | 由 G1 派生 + 协议语义 | 纯透传下设备发出的每帧都会到达 → msgid 必然连续。阈值仅用于吸收「msgid 按命令类别独立计数」「回绕边界」这类**非丢帧**现象，因此脚本额外提供**按 (op,type) 分组**视图，只有分组后仍超标才判丢帧 |
| msgid 分组最小样本 20 帧 | 统计经验值 | 样本太少时 1 次跳号就可能放大成 5%~50% 的假阳性；可用 `--msgid-min-samples` 调整 |
| warmup = T+10 s（P1） | 评审官口径 + 现场经验 | 上电瞬间 ROM/bootloader 的 `rst:0x…`/`boot:…` 文本走同一路 USB，属于「不属于任何 EDV11P 帧」的字节；算进未归属率会让每次采集都假失败。10 s 覆盖该窗口（`--warmup` 可调） |

### 2.3 已知的「合理失败」与「误判防护」

| 现象 | 脚本行为 | 人工判读要求 |
|---|---|---|
| msgid 不分组时跳号很多、分组后为 0 | 报告判定以分组为准，并打印「msgid 按命令类别独立计数，不是丢帧」 | 允许 PASS，但要在 Gate 记录里写明该现象 |
| msgid 到 `0xFFF0` 回绕到 0 | 不作为跳号（`_expected_next` 已处理） | 无需处理 |
| 静置空场景 0x70 帧数为 0 | 只要仍有其它 op 帧在跑，判定不受影响 | 必须确认「雷达确实在发帧」（帧率 > 0），否则是采集配置问题（上报间隔为 0） |
| 整段一帧都没解出来 | 直接判 FAIL（有效帧数检查） | 说明桥接/接线/波特率有问题，先排硬件再谈完整率 |
| 离线 `--file` 的「时间点」 | 按字节位置线性插值到 `--duration` | 只用于对齐/画图，**不代表真实到达时刻**（报告 warnings 已注明） |
| 离线 `--file` 且未给 `--duration` | 无时基 → 自动 `disable_warmup()`，未归属率从流首起算 | 此时头部的 bootloader 文本会被算成未归属字节；判 FAIL 前先确认不是这个原因 |
| 未归属率落在 0~0.1% | 判 **WARN**（不 FAIL），并写入 warnings | 必须在 Gate 记录里点名「哪几个 unparsed 段 / 哪类坏帧」并给出归零计划 |
| 文案里出现 `LED` / `FAILED` 等大写词 | **不是误报**：`L-E-D` 里的 `E`=0x45、`D`=0x44，打印 "LED" 就会产生 45 44 | 这也是横幅门禁会报出 36 处 printf 的原因；桥接构建必须保证这些 printf 不被调用 |

### 2.4 Gate-2 主证据判据（可直接引用的一句话）

> **Gate-2 主证据 = T-FC-01 的「未归属字节率 = 0」且「帧完整率 ≥ 99.9%」，同时满足「重同步绝对次数 ≤ 3 次/30 分钟」与「msgid 跳号率 < 0.1%」，且 T-FC-10 横幅门禁 PASS；四项数值均由 `tools\edv11p_frame_check.py` 输出 JSON 的 `checks[]` 直接给出，进程退出码为 0。**

### T-FC-02 　单人进出多次（P0）

## 五、用 `unparsed_*.bin` 反查污染源（重点）

`unparsed_*.bin` 是「一段连续的、无法构成合法 EDV11P 帧的字节」。它可能来自：串口误码、帧被截断、**或者是有人往数据流里写了非协议内容**（日志、`printf`、`esp_log`）。
排查顺序如下：

> **先做静态门禁再上板**：如果 `--check-banner` 已经报出「横幅/引脚表文案含 45 44」，那就不用等上板，直接按 T-FC-10 修文案/确认开关。
> 运行期的 `unparsed` 段是用来抓「静态查不出来」的污染（例如某条错误分支里的 `ESP_LOGE`、第三方库自己的 `printf`）。

### 5.1 三步定位法

```powershell
# ① 看报告里这一段的位置、长度、可打印比例、特征串
#    JSON 里 unparsed.segments[i] = {offset, size, printable_ratio, ascii, pollution_markers}

# ② 直接看字节
Format-Hex unparsed_1.bin | Select-Object -First 8

# ③ 判断「是不是文本」
#    可打印比例 > 0.7 且能看到成句的英文/数字 → 极可能是日志
#    可打印比例 < 0.3 且高位字节多 → 更像误码/截断的帧体
```

```
     hex: 45 44 00 0D 00 04 A2 10 00 02 00 02 AF 00 01 02 03 4C 4F 47 3A 45 44 4B 36 30 20 62 72 69 64 67 65 20 62 6F 6F 74 0D 0A
     ascii: ED...............LOG:EDK60 bridge boot..
     ⚠ 疑似污染特征: ['EDK60']
     → 已存盘: logs\edv11p\unparsed_1.bin
```

**读法（关键）**：

1. ascii 里能读出成句的 `LOG:EDK60 bridge boot` → 这是**文本日志**，不是二进制帧体。
   （这一段前半截 `45 44 00 0D 00 04 A2 10 …` 是一个被拒的坏帧帧体，后半截才是日志，所以整段可打印比例只有 0.65 —— **低比例不代表没污染**，工具对 `EDK60` 这类强特征是无条件上报的。）
2. 注意 `45 44` 恰好是 `EDK60` 的前两个字母（`E`=`0x45`、`D`=`0x44`）——**ASCII 文本 "EDK60" 本身就是 EDV11P 的帧头**。这就是为什么「固件打印一行带项目名的日志」会立刻制造一次**假同步**：解析器把 `ED` 当帧头，把后面的 `K6`（`0x4B 0x36` = 19254）当长度 → 报「长度非法（>4096）」→ 丢字节 → 重同步。
3. 因此判定口径是：**只要有 `EDK60` 这类文本出现在 unparsed 段里，就说明固件日志仍在往数据流写**，属于固件侧的 P0 缺陷，桥接不算通过。
4. 定位责任人：把该段的 `offset`（字节流偏移）与采集时刻对照 `--csv` 的 `elapsed_s`，即可知道污染发生在第几秒、间隔是否规律（规律 = 周期打日志；突发 = 事件打日志 / 出错打日志）。
5. 修复方向（交嵌入式工程师）：控制台输出改走另一路（USB 第二控制台保持开启但**不产生字符**）、关掉该模块的 `ESP_LOG` 等级、或使用不带日志的 release 配置——**不要**用 `CONFIG_ESP_CONSOLE_SECONDARY_NONE` 关闭第二控制台（历史坑：会导致系统启动卡死、USB 不枚举，见 `docs/EDK60-pitfalls.md`）。

> **特征串分级（工具实现）**：`EDK60` / `ESP-IDF` / `esp_idf` / `bridge:` / `radar_` / `rst:0x` / `stack:` 这类 **≥5 字节的强特征命中即报**（二进制误码凑不出来）；
> `I (` / `W (` / `E (` / `boot:` 这类 2~3 字节的弱特征只在整段可打印比例 ≥ 0.7 时才报，避免误报。

### 5.3 常见 unparsed 段的判读对照表

| ascii / 特征 | 判断 | 处置 |
|---|---|---|
| `I (1234) tag: ...` / `W (` / `E (` / `ESP-IDF` | ESP-IDF 日志混入 | 固件 P0，改日志输出路径 |
| `EDK60` / `bridge:` / `radar_` 等自定义字符串 | 项目自己的 `printf`/`ESP_LOGI` | 同上 |
| `rst:0x...` / `boot:...` | 芯片复位日志 | 说明采集期间发生过复位 → 查电源/看门狗（同时看 T-FC-07） |
| 乱码但可打印率 < 0.3、长度几十字节 | USB/UART 误码，或某帧被截断 | 看 `bad_frames` 计数；偶发 1~2 次可接受，持续出现要查线材/供电 |
| 长度恰好 = 某个 0x70 帧的一半 | 帧被截断（固件缓冲/抓取窗口切断） | 检查 `truncated` 计数与 `--save-raw` 的边界 |

## 六、执行建议

| 项 | 内容 |
|---|---|
| 顺序 | **T-FC-10（横幅门禁，1 min，不需要硬件，先过准入）** → T-FC-05（自测，5 min）→ 3.0 准备 → T-FC-04（10 min，先排除污染）→ **T-FC-09（与 T-FC-01 同一次 30 分钟采集即可同时取证）** → T-FC-01（30 min）→ T-FC-02（10 min）→ T-FC-03（15 min）→ T-FC-06（5 min）→ T-FC-07/T-FC-08（按需） |

## 七、缺陷分级与结论映射（配合 Gate-2 裁定）

| 现象 | 严重级 | 对 Gate-2 的影响 |
|---|---|---|
| **未归属字节率 ≥ 0.1%** | P0 | NO-GO（R1 口径：流里掺了不属于任何帧的字节） |
| **未归属字节率 0 ~ 0.1%（WARN）** | P1 | GO-with-conditions，必须点名来源并给出归零计划 |
| **重同步绝对次数 > 3 次/30 min** | P0 | NO-GO（有字符持续插入；比率可能还「好看」） |
| 坏帧率 ≥ 0.1% 或 帧完整率 < 99.9% | P0 | NO-GO，桥接方案不成立（丢字节 = 桥接 bug） |
| **横幅门禁严格模式 FAIL（文案含 45 44）** | P1 | 先修/确认开关；未处置前不得用 30 分钟 PASS 作为 Gate-2 证据 |
| **桥接 demo 里出现 printf/ESP_LOGx** | P0 | NO-GO（固件自己在写数据流） |
| `unparsed` 段里出现文本/日志特征（如 `EDK60`） | P0 | NO-GO，日志污染未解决，上游上位机会不断重同步 |
| 重同步次数 > 0 但 ≤ 上限、且已定位为偶发误码 | P1 | GO-with-conditions（记录现象 + 复测计划） |
| 0x70 载荷异常 > 0 | P0 | NO-GO（帧被搞乱，人数统计不可信） |
| 静置场景出现 `max 目标数 > 0` | P1 | 需解释（环境有人 / 遮挡物 / 灵敏度设置），不必然阻断 |
| msgid 不分组超标、分组达标 | — | 不算缺陷，写进 Gate 记录的「已知现象」 |
| 采集时长不足 30 分钟 | P1 | 只能给 GO-with-conditions，证据需补齐 |

**Gate-2 结论口径**：T-FC-01（同一份数据即 T-FC-09）退出码 0 且 `未归属字节率 = 0`、T-FC-10 已处置、T-FC-04 无污染 → 视为 G1/S3/R1 达标；否则按上表落级。

## 八、附：脚本输出物与归档
