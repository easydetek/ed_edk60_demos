## 一、测试目的

固件侧**不做任何解析**，只把雷达字节流从 UART 搬到 USB。因此「桥接是否诚实」只能由 PC 侧客观统计证明。本测试回答四个问题：

1. **有没有丢字节 / 丢帧？** → 坏帧率、帧完整率、重同步次数、未归属字节率。
2. **转义处理对不对？**（EDV163 独有）→ 转义错误数、还原的转义对数、含转义帧的正文逐字节对账。
3. **帧有没有被搞乱？** → 每帧声明长度 / TLV 长 / 校验是否自洽；0x81 载荷长度是否等于 `1 + 步长 × count`。
4. **有没有别的东西混进流里？** → `unparsed_*.bin` 里的非协议字节是什么（重点：固件日志）。
   注：EDV163 上「混进一行日志」比 EDV11P 更致命 —— 因为日志的换行符 `0x0A` **就是帧尾**。

**分工边界**：本工具只证明「桥接 + 转义」这一段链路完整；水位数值准不准（挂高标定、水面回波质量、网页换算）由网页端用例与卷尺实测（本计划 T-FC-02/03）负责，两者不可互相替代。

## 二、协议要点速查（与 EDV11P 不同的三处，全部是新增风险）

### 2.1 帧结构、转义、载荷

```
256000 8N1，大端。长度字段 = 整包字节数（按【转义前】计）

0x45 0x44 | 长度(2) | msgid(2) | op(1) | type(1) | TLV长(2) | data N | 校验(1) | 0x0A
   2      +   2     +    2     +   1    +   1     +    2      +   N    +   1    +  1
   ⇒ 长度 = 12 + N，最小 12，最大 256

校验 = 转义前「帧头 → data 末」逐字节求和 & 0xFF（不含校验自身与帧尾）
转义 = 正文 0x0A → 0x09 0x01、0x09 → 0x09 0x00；帧尾 0x0A 不转义
组包顺序（edv163.c edv163_pack_data）：
      算长度 → 算校验 → 对「帧头…校验」整段转义 → 最后贴帧尾 0x0A
接收侧必须反序：先还原，再按「转义前长度」切帧，再验校验
```

| op | 含义 | type | 含义 |
|---|---|---|---|
| 0xA0 | GET 参数获取 | 0x01 / 0x02 | 产品信息 / 模块信息 |
| 0xA1 | SET 参数设置 | 0x11 / 0x17 / 0x18 | 检测延时 / 上报频率(100ms) / 工作模式 |
| 0xA2 | REPORT 应答 | 0x25 / 0x26 / 0x27 / 0x28 / 0x29 | 挂高 / 检测高度 / 检测范围 / 自动测高 / 屏蔽区 |
| 0xA3 | STATUS 主动上报 | **0x81** | **上报数据（水位来源）** |
| 0xA4 / 0xA9 | 透传 / ACK | | |

0x81 载荷（**以驱动实现为准，7 字节/通道**）：

```
count(1B) + count × { channel(1) | delay_presence(1) | target_state(1) | motion_direction(1)
                      | target_distance(2B 大端, mm) | target_angle(1B 有符号, 度) }
⇒ tlv_len = 1 + 7 × count：1 通道 8、2 通道 15、3 通道 22
水位：level_mm = mount_mm − target_distance_mm（distance = 0 表示无目标，不计入统计）
```

### 2.2 已知文档缺陷：0x81「每通道 8 字节」是笔误，实际是 **7 字节**

> 这一条会影响**下游解析器**（网页 `release/level.html`、任何网关/上位机），必须留档。

| 项 | 内容 |
|---|---|
| 矛盾点 | 协议文档 §3 与部分任务书写作「每通道 **8B**」，但紧接着列出的字段只有 **6 个、合计 7 字节**；同一文档的 type 表却写 `0x25` 挂高为 2B、`0x29` 屏蔽区为「1B 数量 + N×13B」，说明作者本就按**紧凑打包**描述 |
| 实现证据 | `radar/edv163.h`：`edv163_channel_data_t` 为 `__attribute__((packed))`，字段 `channel / delay_presence / target_state / motion_direction / target_distance(2) / target_angle(1)` = **7 字节**（packed 无填充，sizeof = 7） |
| 解析证据 | `radar/edv163.c` L372-390：读到 `channel_count` 后按 **7 字节/通道**顺序 `index++` 读取；且**从未用 tlv_len 校验数据区长度** |
| 推导结论 | 真实 `tlv_len = 1 + 7 × count`（1 通道 → `0x0008`、2 通道 → `0x000F`、3 通道 → `0x0016`）；若按 8B 实现，2 通道帧会整体错位 1 字节，距离/角度全错 |
| 工具处理 | `--channel-stride {auto,7,8}` 默认 `auto`：用**首个 0x81 帧的实收长度**反推步长。锁定 **7 = 正常**（不告警）；锁定 **8 = 告警**（说明固件按文档口径发，与驱动解析冲突，必须先对齐）；两种口径都除不尽 = 载荷异常（计入 P7） |
| 对下游的结论 | **网页端与任何解析器一律按 7B/通道实现**；协议文档需由组件库维护者更正（文档不在本仓库，本项目只提供证据不改他人文件） |
| 取证方式 | 上板抓到真实帧后，把 JSON 里 `report_0x81.channel_stride` 的值 + `by_op_type` 帧数一并提交，即可证明实测步长 |

> 另有两条与 EDV11P 不同的实现细节，写测试用例时要记住：
> 1. `edv163_data_t.data_changed` 是**固件本地标志**，代码里另行置 1，**不在串口载荷里** —— 载荷第一字节就是 `channel_count`，前面没有 `data_changed`。
> 2. 驱动收到帧后**不做转义还原也不太校验 tlv_len**（它按「在线长度」直接切帧），这意味着**转义是否被正确处理，只能由 PC 侧工具证明** —— 这正是本计划的核心。

## 三、判定阈值与来源

### 3.1 阈值表（P0 前提 + 八条硬判据；脚本内 `THRESHOLDS` 常量，`--help` 与报告同源输出）

| 优先级 | 指标 | 计算口径 | 阈值 | 失败含义 |
|---|---|---|---|---|
| **P0** | 有效帧数 | 合法帧计数 | ≥ 1 | 整段一帧都没解出来 → 采集无效，其余判据 SKIP；先排波特率 / 接线 / 上电 |
| **P1** | **转义错误数** | 事件计数，见 3.3 | **= 0** | 转义层被破坏；此时长度/校验都在**错误切分**上算出，必须先修转义 |
| **P2** | **未归属字节率** | (窗口内收字节 − 窗口内合法帧**在线**字节) / 窗口内收字节；窗口从 **T+10 s** 起算（`--warmup` 可调） | **= 0 → PASS**；0 < x < 0.1% → **WARN**；≥ 0.1% → **FAIL** | 数据流里混进了不属于任何合法帧的字节（坏帧 / 日志 / 误码） |
| **P3** | 重同步绝对次数 | 重同步事件计数 | ≤ max(1, round(3 × 时长/1800 s))，**30 分钟 = 3 次** | 有字符在「持续」插入流里；比率能摊薄异常，绝对次数不能 |
| **P4** | 坏帧率 | 坏帧数 /（好帧数 + 坏帧数） | < 0.1% | 帧被传坏（长度 / 校验 / TLV / 转义 / 帧尾 / 截断） |
| **P5** | 帧完整率 | 好帧数 /（好帧数 + 坏帧数 + 重同步） | **≥ 99.9%** | 主指标不达标（丢字节 = 桥接 bug） |
| **P6** | msgid 跳号率 | 跳号次数 / 组内帧数（按 (op,type) 分组取最大组） | < 0.1% | 帧序中断 → 疑似丢帧（分组后仍超标才算） |
| **P7** | **0x81 载荷自洽率** | 长度自洽的 0x81 帧 / 0x81 帧总数；自洽 = 载荷长度 `== 1 + 步长×count` | **= 100%** | 帧被截断或长度字段被改 → 距离/水位不可信 |
| **P8** | **0x81 上报帧数** | 0x81 帧计数 | **≥ 1** | 水位 demo 没有 0x81 就没有距离数据（只收到 ACK/SET 应答说明雷达没在上报） |

坏帧**六分类**分别计数（报告逐项列出）：长度非法（<12 或 >256）、校验和错误、TLV 长度与帧长不符、**转义错误**、帧尾不是 0x0A、截断帧。这些字节**都算「未归属」**。

结论规则：P0 + P1..P8 全部 PASS 才是 **PASS**；任一 FAIL 即 **FAIL**；样本不足判 **N/A**（不阻断，但要在 Gate 记录里说明），**WARN 不阻断但必须逐条记录**。退出码：`0` = PASS、`1` = FAIL、`2/3/4` = 参数/环境错误。

### 3.2 阈值来源说明（为什么是这几个数）

| 阈值 | 来源 | 说明 |
|---|---|---|
| 转义错误 = 0（P1） | **协议 §2.4 转义规则 + 风险 S1（P=4/I=5，评分 20，本项目最高）** | EDV11P 无此层，逐字照抄旧方案必然踩坑：任何 0x09/0x0A 数据字节处理错，整帧长度与校验都会连带错。转义是「全或无」的，故零容忍 |
| 未归属字节率 = 0（P2） | 项目口径「纯字节透传，一个多余字节都不该有」+ 与 EDV11P R1 口径一致 | 判据按**在线字节**精确归属：合法帧占用多少字节就是多少（含转义膨胀）。转义膨胀也算「已归属」，避免把正常的 `09 00` 误判成垃圾 |
| WARN 窄带 0~0.1%（P2） | 与 P4 同量纲 | 留一个「可解释但不许重复」的窄带：偶发 1~2 字节误码不至于让整场 30 分钟白跑，但必须点名来源 |
| 重同步 ≤ 3 次/30 min（P3） | 由 P2 派生 + 现场经验 | P2 零容忍 ⇒ 理论上应为 0；给 3 次是承认「USB 侧偶发一次读边界错位」，再往上说明有东西在持续插入 |
| 0.1% 坏帧率（P4） | 与 P5 同源（同一份数据的另一切面） | P4 只衡量「帧被传坏」；P5 还把重同步计进分母。两者同看可区分「帧传坏」与「字节被插入/丢失」 |
| 99.9% 帧完整率（P5） | **项目计划五、验收判据 1** | 按上报 100 ms（10 帧/s）× 1800 s ≈ **18000 帧**，0.1% ≈ **18 帧**容错额度，对应「水位曲线不断点」的演示级要求 |
| 0.1% msgid 跳号（P6） | 协议「msgid 递增、应答回显」+ P5 派生 | 纯透传下设备发出的每帧都会到达 → msgid 必然连续。阈值只用于吸收「msgid 按命令类别独立计数」「回绕（0xFFF0→0）」这类**非丢帧**现象，故脚本提供按 (op,type) 分组视图，只有分组后仍超标才判丢帧 |
| 载荷自洽率 = 100%（P7） | **协议 §3 载荷格式 + `edv163.c` L372-390 解析顺序** | 0x81 是唯一带变长嵌套的帧；长度与 `count` 不自洽 ⇒ 距离字段位置错 ⇒ 水位错。步长按实测锁定，兼容 7B/8B 两种口径（见 2.2） |
| 0x81 ≥ 1 帧（P8） | 业务需要 | 没有 0x81 就没有 `target_distance`，水位 demo 无从谈起 |
| msgid 分组最小样本 20 帧 | 统计经验值 | 样本太少时 1 次跳号会放大成 5%~50% 的假阳性；可用 `--msgid-min-samples` 调整 |
| warmup = T+10 s（P2） | 评审口径 + 现场经验 | 上电瞬间 ROM/bootloader 文本走同一路 USB；算进未归属率会让每次采集都假失败。10 s 覆盖该窗口（`--warmup` 可调） |

### 3.3 转义错误统计口径（P1 的唯一输入，必须写清否则无法复核）

工具在**逐帧还原正文**的过程中统计三类事件，**每发生一次记 1**（同一帧命中两类分别计数，所以「各类之和」可能大于「帧数」）：

| 类别（JSON 键） | 定义 | 典型来源 |
|---|---|---|
| `illegal_sequence` **非法转义序列** | `0x09` 之后既不是 `0x00` 也不是 `0x01`（例如 `0x09 0x05`） | 误码把 `0x09 0x0?` 的第二个字节打坏；固件转义表写错；把 `0x09` 当普通数据发 |
| `bare_0a` **帧中途裸 0x0A** | 还没凑够声明长度就遇到 `0x0A` | 日志/printf 的换行符（`\r\n` 里的 `0x0A`）混进流；发送侧漏转义；帧被截断后紧接着出现别的 `0x0A` |
| `dangling_09` **悬空 0x09** | 流在转义序列中途结束（最后一个字节是 `0x09` 却没有转义码） | 抓包窗口/拔线正好切在转义对中间 |

配套的**正向指标**（证明工具真的在还原，而不是「碰巧解对了」）：

| 指标 | 含义 |
|---|---|
| `pairs_restored` | 成功还原的转义对总数（= 线上去掉转义后的净膨胀字节数） |
| `pairs_0a_restored` / `pairs_09_restored` | 其中 `0x09 0x01 → 0x0A` / `0x09 0x00 → 0x09` 各多少次 |
| `frames_with_escape` | 含转义还原的合法帧数（一条 30 分钟采集里这个数应该很可观，见下） |
| `samples[]` | 前 5 个含转义的帧 → `msgid / escapes / declared_len / wire_len / payload_hex`，可逐字节对账 |

> **为什么转义层「每天」都在工作**：`0x81` 单通道帧的 TLV 长度字节是 `0x0008`（不触发），但 `target_distance` 的**高/低字节完全可能是 0x09 或 0x0A**（例如 2569 mm = `0x0A09`，1497 mm = `0x05D9`），校验字节也可能是 `0x09/0x0A`。实测自测合成流里 16 帧就有 4 帧含转义。所以「转义错误 = 0」不是理论要求，是**每一帧都在被检验**的判据。

### 3.4 判据之间的优先级与冲突处理

1. **P0 先短路**：无有效帧时其余判据一律 SKIP，结论 FAIL —— 不能因为「没测到」判通过。
2. **P1 优先级最高**：转义一错，后面的长度/校验统计都建立在错误切分上；此时 P2~P7 的坏值都是 P1 的**后果**，先修转义再看别的。
3. **P2 比「假同步丢帧估算率」严**：P2 按字节精确归属，后者按事件估算 → 冲突以 P2 为准。
4. **P2 与 P4 不重复计分**：坏帧字节本身就算未归属，P4 > 0 必然 P2 > 0 → 先判 P2，P4 只说明「坏在哪一类」。
5. **P3 与比率类冲突以 P3 为准**：短采集里几次重同步能把比率摊到 0.1% 以下，绝对次数照样是缺陷。
6. **P7/P8 只在水位场景生效**：没有 0x81 帧时 P7 记 N/A，但 P8 会 FAIL（水位 demo 必须有距离数据）。
7. **WARN 的处理**：`0 < 未归属率 < 0.1%` 记 WARN —— 不改变 PASS，但 Gate 记录里必须写清「未归属字节数 + 来源（哪个 unparsed 段 / 哪类坏帧）」并纳入归零计划。

### 3.5 不影响 PASS/FAIL 但会进 warnings 的观察项

- 出现未识别 op/type；0x81 通道数 = 0；全程距离样本为 0（无水面回波）。
- 0x81 帧间隔 > 5× 中位间隔（疑似大面积丢帧或雷达暂停上报）。
- 采集时长不足 `--duration` 的 90%；单段垃圾字节 > 1 KiB（疑似日志污染）。
- 0x81 步长锁定为 **8**（说明固件按文档口径发，与驱动 7B 解析冲突 → 见 2.2）。

### 3.6 Gate 判据（可直接引用的一句话）

#### 4.0.3 前置检查清单（每条上板用例都走一遍，避免把「没数据」当「桥接坏」）

1. 模组插在 **H3**，丝印 `RADAR` 红灯亮（雷达已上电，EN = IO14 高）。
2. 板子烧的是 `radar_bridge_edv163`，且 `sdkconfig` 里波特率是 **256000**（沿用 921600 会一帧都收不到）。
3. 设备管理器能看到原生 USB 串口（VID 0x303A），记下 COM 号。
4. **让雷达有帧可发**：工作模式 `0x18` = 1、上报频率 `0x17` = 100 ms（10 帧/s）。
   ⚠ 本工具**只读不写**，不主动发 SET 帧；工作模式/上报频率/挂高需要由网页端或专用上位机脚本下发，
   并在开测前**一次性**设好（避免测试中途的 SET 应答混进统计）。
5. **挂高要标定**：用卷尺量「传感器 → 水面」实际距离，反算挂高 = 实测距离 + 当时水位高度；
   把最终挂高写进 `--mount-mm`（默认 2000）。**挂高与 `--mount-mm` 不一致会让水位系统性偏移**。
6. 采集期间不要开其它串口工具（同一 COM 被占用会读不到数据）；笔记本接电源、关休眠、关 USB 选择性挂起。

## 六、与 EDV11P 版本的差异（照抄旧方案会踩的三个坑）

| 维度 | EDV11P（人数/轨迹） | **EDV163（水位）** | 对测试的影响 |
|---|---|---|---|
| 波特率 | 921600 | **256000** | 沿用 921600 → 一帧都收不到，P0 直接 FAIL；工具 `--baud` 默认已改成 256000 |
| 帧尾 | **无** | **固定 0x0A** | 新增「帧尾错误」坏帧类别；裸 0x0A 是**分帧唯一标志** |
| 转义 | **无** | **有**：`0x0A→09 01`、`0x09→09 00`（帧尾不转义） | 新增 P1 硬判据 + 三类转义错误统计；**在线字节数 ≠ 声明长度**，「帧完整性」必须在还原后再判 |
| 长度口径 | 整包字节数（无转义，直接切） | 整包字节数但按**转义前**计 | 解析必须先还原再按声明长度切；直接用在线字节数切帧会错位 |
| 校验 | 求和 & 0xFF（帧内末字节） | 求和 & 0xFF（**校验字节本身也可能被转义**） | 自测专门造了一帧「校验 = 0x0A 被迫转义」的用例 |
| 上报载荷 | `0x70`：zone + 目标 x/y/z | `0x81`：count + 每通道 6 字段（**7B**） | 载荷自洽判据（P7）取代原来的「目标数」统计 |
| 业务换算 | 无（直接展示坐标） | **水位 = 挂高 − 距离**（需 `--mount-mm`） | 新增水位 min/median/max、CSV 时间序列；挂高错 → 全量系统偏差 |
| 判据条数 | P0 + 6 条 | **P0 + 8 条**（新增 P1 转义、P7 载荷自洽、P8 0x81 帧数；坏帧由 4 类扩到 6 类） | Gate 引用时要写清用的是 EDV163 的判据版本 |
| 污染杀伤力 | 日志插在帧之间，只制造假同步 | 日志换行 `0x0A` = 帧尾 → **帧中途裸 0x0A** | 日志污染的后果更严重，T-FC-04 的阳性对照必须做 |

## 七、用 `unparsed_*.bin` 反查污染源

`unparsed_*.bin` 是「一段连续的、无法构成合法 EDV163 帧的字节」。可能来自：串口误码、帧被截断、**或有人往数据流里写了非协议内容**（日志 / `printf` / `esp_log`）。

### 7.1 三步定位法

```powershell
# ① 看报告里这一段的位置、长度、可打印比例、特征串
#    JSON: unparsed.segments[i] = {offset, size, printable_ratio, ascii, pollution_markers}
# ② 直接看字节
Format-Hex logs\edv163\unparsed_1.bin | Select-Object -First 8
# ③ 判断：可打印率 > 0.7 且能读出成句英文 → 日志；< 0.3 且高位字节多 → 误码/截断帧体
```

### 7.2 实测样例（本工具在自测合成流上的真实输出，可复现）

```
【无法解析的字节段】
  #2 偏移 327  25 字节  [garbage_or_badframe]  可打印率 0.92
     hex: 00 01 4C 4F 47 3A 45 44 4B 36 30 20 62 72 69 64 67 65 20 62 6F 6F 74 0D 0A
     ascii: ..LOG:EDK60 bridge boot..
     ⚠ 疑似污染特征: ['EDK60']
     → 已存盘: logs\edv163\unparsed_2.bin
```

读法：

1. `ascii` 能读出成句的 `LOG:EDK60 bridge boot` → **文本日志**，不是帧体。
2. `45 44`（ASCII `ED`）正好是**帧头**；`EDK60` 里的 `E`=`0x45`、`D`=`0x44`，所以打印一行带项目名的日志就会立刻制造**假同步**（后面 `K6`=`0x4B36` 被当长度 → 长度非法）。
3. **本行末尾的 `0D 0A` 里的 `0A` 是 EDV163 的帧尾** —— 即使日志内容里没有 `ED`，只要日志有换行，也会被判成「帧中途裸 0x0A」。
4. 判定口径：**只要 `unparsed` 段里出现文本特征或转义错误里出现 `bare_0a`，就说明固件日志仍在写数据流** → 固件侧 P0 缺陷，桥接不算通过。
5. 修复方向（交嵌入式）：控制台输出改走另一路（USB 第二控制台**保持开启但不产生字符**）、关掉该模块的 `ESP_LOG` 等级、或用不带日志的 release 配置 —— **不要**用 `CONSOLE_SECONDARY_NONE` 关掉第二控制台（历史坑：启动卡死、USB 不枚举，见 `docs/EDK60-pitfalls.md`）。

### 7.3 判读对照表

| ascii / 特征 | 判断 | 处置 |
|---|---|---|
| `I (…` / `W (` / `E (` / `ESP-IDF` | ESP-IDF 日志混入 | 固件 P0，改日志输出路径 |
| `EDK60` / `bridge:` / `radar_` 等自定义串 | 项目自己的 `printf`/`ESP_LOGI` | 同上 |
| `rst:0x…` / `boot:…` | 芯片复位日志 | 采集期间发生过复位 → 查电源/看门狗（同时看 T-FC-07） |
| 乱码、可打印率 < 0.3、几十字节 | 误码，或某帧被截断 | 看 `bad_frames`；偶发 1~2 次可接受，持续出现查线材/供电 |
| 段长恰好 = 某个 0x81 帧的一半 | 帧被截断（缓冲/抓取窗口切断） | 检查 `truncated` 计数与 `--save-raw` 边界 |
| 段内出现 `09 0?` 之外的 `09 xx` | 转义表写错 / 误码位于转义对 | 看 `escape.error_kinds` 的 `illegal_sequence` 计数 |

## 九、缺陷分级与结论映射

| 现象 | 严重级 | 对 Gate 的影响 |
|---|---|---|
| **转义错误 > 0** | **P0** | NO-GO：转义层坏了，帧切分与校验全部不可信（本项目最高风险 S1） |
| **未归属字节率 ≥ 0.1%** | P0 | NO-GO（流里掺了不属于任何帧的字节） |
| 未归属字节率 0~0.1%（WARN） | P1 | GO-with-conditions，必须点名来源并给出归零计划 |
| **重同步绝对次数 > 3 次/30 min** | P0 | NO-GO（有字符持续插入；比率可能还「好看」） |
| 坏帧率 ≥ 0.1% 或帧完整率 < 99.9% | P0 | NO-GO，桥接方案不成立（丢字节 = 桥接 bug） |
| **0x81 载荷自洽率 < 100%** | P0 | NO-GO，距离/水位字段位置不可信 |
| **0x81 帧数 = 0** | P0 | NO-GO，没有水位数据（先查工作模式 `0x18`、上报频率 `0x17`） |
| `unparsed` 段出现日志特征 **或** 转义错误里出现 `bare_0a` | P0 | NO-GO，日志污染未解决 |
| 0x81 步长锁定为 **8**（与驱动 7B 冲突） | P1 | 必须先与组件库对齐协议再判；网页解析器按 7B 实现（2.2） |
| 水位稳态偏差 ≥ 20 mm（卷尺实测对比） | P1 | GO-with-conditions：先复核挂高标定与水面回波质量，再判测距精度 |
| 重同步 0 < n ≤ 上限，且已定位为偶发误码 | P1 | GO-with-conditions（记录现象 + 复测计划） |
| msgid 不分组超标、分组达标 | — | 不算缺陷，写进 Gate 记录的「已知现象」 |
| 采集时长不足 30 分钟 | P1 | 只能给 GO-with-conditions，证据需补齐 |

**结论口径**：T-FC-01 退出码 0（= P1/P2/P5/P7/P8 全 PASS）、T-FC-03 证明「转义路径被真正走过」、T-FC-04(a) 无污染、T-FC-04(b) 阳性对照能抓到 → 视为桥接链路达标；否则按上表落级。
