## 1. 与 EDV11P 版本（track.html）的关键差异

| 维度 | track.html（EDV11P） | level.html（EDV163） |
|---|---|---|
| 波特率 | 921600 | **256000** |
| 帧 | `45 44 | len | msgid | op | type | tlvlen | data | ck`，**无帧尾** | `45 44 | len | msgid | op | type | tlvlen | data | ck | **0x0A**` |
| 长度域含义 | 整包字节数 = 11 + dataLen | 整包字节数 = **12 + dataLen**（把帧尾算进去） |
| 校验和位置 | 末字节 | **倒数第 2 字节**（末字节是帧尾 0x0A） |
| 转义 | **无** | **有**：`0x0A → 09 01`、`0x09 → 09 00`，帧尾不转义 |
| 帧界识别 | 靠长度域 | 靠长度域 **+ 0x0A**，且必须把「转义序列 09 01」与「真帧尾」区分开 |
| 主视图 | 俯视轨迹图 | **水位时间曲线 + 竖向水位柱 + 大字读数** |
| 业务换算 | 无（画坐标） | **水位 = 挂高 − target_distance** |

> 结论：**不能复用 track.html 的解析器**。长度与校验和都必须在**还原后**的字节上计算，
> 直接把 track.html 的 `EdvParser` 搬过来会在「正文含 0x0A/0x09」时全线崩溃。

## 2. 帧结构（发送与接收同一套，逐字节对齐 C 实现）

```
 0        2        4        6    7    8        10            N+10       N+11
 +--------+--------+--------+----+----+--------+------------+----------+--------+
 |45 44   | 长度   | msg id | op |type| TLV长度|  数据区 N  |  校验和  | 0x0A   |
 | 2B     | 2B BE  | 2B BE  | 1B |1B  | 2B BE  |  N B       |   1B     | 帧尾   |
 +--------+--------+--------+----+----+--------+------------+----------+--------+
 长度 = 12 + N（**含帧尾**，转义前计算）；校验和 = Σ(帧头..数据区末) & 0xFF
 组包顺序：算长度/校验和 → 追加校验和 → 对「帧头..校验和」整段转义 → 追加帧尾 0x0A
```

| 字段 | 偏移 | 长度 | 编码 | 说明 | 来源 |
|---|---|---|---|---|---|
| 帧头 | 0 | 2 | `0x45 0x44` | 固定 | 协议文档第 18 行；C 实现 `edv163.h:30-31` |
| 长度 | 2 | 2 | uint16 **大端** | **12 + 数据区长度**，最小 12、最大 256，**含帧尾** | 协议文档第 21 行；C `edv163.h:33-34`、`edv163.c:108` |
| msg id | 4 | 2 | uint16 大端 | 递增；应答回显 | 协议文档第 22 行；C `edv163.c:122-123` |
| op | 6 | 1 | uint8 | `A0 GET / A1 SET / A2 REPORT / A3 STATUS / A9 ACK` | 协议文档第 24-33 行 |
| type | 7 | 1 | uint8 | 见 §3 | 协议文档第 35-58 行 |
| TLV 长度 | 8 | 2 | uint16 大端 | 必须 = 长度 − 12 | C `edv163.c:127-128` |
| 数据区 | 10 | N | 视 type | — | — |
| 校验和 | 10+N | 1 | uint8 | `Σ(帧头..数据区末) & 0xFF`，**按还原后字节算** | 协议文档第 60-66 行；C `edv163.c:135` |
| 帧尾 | 11+N | 1 | `0x0A` | **固定 0x0A，永不转义** | 协议文档第 18、77 行；C `edv163.c:139` |

> ⚠ 与 C 实现的一处**已知缺陷**（不影响本页，但要记录）：C 实现的接收路径
> （`edv163.c:337-345`）直接用**未还原**的原始字节校验帧尾与校验和，**没有做转义还原**。
> 若设备上报帧正文恰好含 `0x0A`/`0x09`，固件侧会判帧尾/校验和错误。本页按协议文档
> 正确实现「先还原再校验」，因此**本页比固件侧更健壮**；此差异列入 §9 上板待确认项 U3。

### 3.1 op 取值口径

- 周期上报是 **`op = 0xA3`（STATUS）+ `type = 0x81`**；C 实现 `edv163.c:369`
  `op == EDV163_PRO_OP_STATUS && cmd == EDV163_PRO_TYPE_REPORT_DATA`。
- 对 GET/SET 的回复是 **`op = 0xA2`（REPORT）**，并回显 msg id（±1 容错，C `edv163.c:358`）。
- 本页主路径按 0xA3，同时**兼容 0xA2 + 0x81**（防御性，避免固件版本差异导致无数据）。
  判据在 `handleFrame`（1836）：`f.type === 0x81 && (op === 0xA3 || op === 0xA2)`。

### 3.2 0x81 载荷：**每通道 7 字节**（⚠ 协议文档「8 字节」是笔误）

```
count(1B) + count × { channel:1, delay_presence:1, target_state:1, motion_direction:1,
                      target_distance:2(BE, mm), target_angle:1(int8, 有符号) }   ← 7B/通道
tlv_len 必须 = 1 + 7 × count   （count=1 → 8；count=2 → 15；count=3 → 22）
```

| 偏移（通道首字节起） | 长度 | 字段 | 类型 | 说明 |
|---|---|---|---|---|
| 0 | 1 | channel | uint8 | 通道号 |
| 1 | 1 | delay_presence | uint8 | 0 无人 / 1 有人 |
| 2 | 1 | target_state | uint8 | 0 无人 / 1 静止 / 2 运动 |
| 3 | 1 | motion_direction | uint8 | 0 静止 / 1 靠近 / 2 远离 |
| 4 | 2 | target_distance | uint16 **BE** | mm（水面距离） |
| 6 | 1 | target_angle | **int8** | 度，有符号（>127 时 −256） |

**为什么以 7 为准（U1 已裁决）**

| 证据 | 内容 |
|---|---|
| C 实现 `edv163.c:372-390` | `channel_count = buf[index++]`，随后循环里逐字段读 1+1+1+1+2+1 = **7 字节** |
| 协议文档 §3 正文 | 写「每个通道 8 字节」，但**同段表格只列 7 个字段**（自相矛盾） |
| 结论 | **7B 为准**；解析器 `parseReport81`（842）里 `expect = 1 + 7×count`，与 `tlv_len` 比对，不一致即判「载荷异常」并计数（`stats.badPayload`），**绝不按 `tlv_len/8` 推算通道数** |

> 若将来遇到 stride=8 的固件，`parseReport81` 的报错文案会明确写出
> 「按本帧推算每通道 8B = 旧文档「8B」口径（固件版本不同？）」，
> 属于**显式失败**而不是静默渲染垃圾数据。自测用例 C8 专门锁这条。

## 4. 转义处理算法（本版最核心的一段，含行号）

### 4.1 规则（协议文档第 68-77 行；C `edv163.c:60-90`、`edv163.c:138-139`）

| 方向 | 规则 |
|---|---|
| 发送（转义） | 正文中 `0x0A → 0x09 0x01`、`0x09 → 0x09 0x00`；**帧尾 0x0A 不转义** |
| 接收（还原） | `0x09 0x01 → 0x0A`、`0x09 0x00 → 0x09`；`0x09` 后跟其它字节 = **非法转义** |
| 作用范围 | 帧头 … 校验和（共 `len-1` 字节），帧尾在转义**之后**追加 |
| 长度/校验和 | 一律按**还原前**（即还原后字节序列）计算，与线上字节数无关 |

### 4.2 实现三段

| # | 函数 | 行号 | 要点 |
|---|---|---|---|
| 1 | `escapeBytes(bytes)` | **570** | 单向扫描，命中 `0x0A`/`0x09` 各展开成 2 字节；**不含帧尾**（帧尾由 `createFrame` 追加） |
| 2 | `unescapeBytes(escaped)` | **586** | 反向扫描，返回 `{ok, bytes, escaped}`；末尾孤立 `0x09`、`0x09 + 非 00/01` 都返回 `ok:false`（供自测与调试用；**接收主线不调用它**，见 #3） |
| 3 | `EdvParser._tryDecode(pos)` | **750** | 接收主线的**流式**还原 + 校验（不预先整段还原，避免半帧时反复拷贝） |

### 4.3 接收状态机（`_tryDecode`，750-840）——「按 0x0A 找帧界如何区分转义序列」

```
从 pos（已确认 45 44）开始，逐"线上"字节推进，同时累积还原后的 out[]：
  out.length 达到 4  → 读出长度域 lenField = (out[2]<<8)|out[3]
                       不在 12..256 → badLength++，skip 1 重同步
  out.length 达到 lenField-1 → 帧头..校验和收齐，跳出循环

  循环内每个线上字节：
    0x09  → 必须跟 0x00 / 0x01（否则 badEscape++，skip 1 重同步）
            0x09 0x00 → 还原出 0x09（1 字节）；0x09 0x01 → 还原出 0x0A（1 字节）
    0x0A  → 这是**真帧尾**（因为它前面没有 0x09 引导）：
            若此时 out 还没收齐 → truncated++（截断帧），skip 到该 0x0A 之后
    其它  → 原样记入 out

跳出后：
  下一个线上字节必须是 0x0A          否则 badTrailer++，skip 1
  校验和 = Σ out[0 .. lenField-3]   与 out[lenField-2] 比对，不等 → badChecksum++，skip 1
  tlv_len = out[8..9] 必须 = lenField-12，否则 badTlv++，skip 1
  数据区 = out[10 .. lenField-3]
```

**三个关键判据**

1. **`0x0A` 只在「没有 0x09 引导」时才算帧尾** —— 正文里的 `0x0A` 一定以 `09 01` 出现，
   被 ② 分支吃掉，不会被误判成帧尾。自测 C3（正文含 `0x0A`/`0x09`）与 C6（噪声里含裸 `0x0A`）锁这条。
2. **长度域与校验和都用还原后的 `out[]`** —— 自测 C3 的线上 23 字节对应声明长度 20 字节，
   若按线上字节算长度会直接判为非法。
3. **任何非法形态都只 skip 1 字节重同步** —— 不 `flush` 缓冲区，不整段丢弃：
   截断帧（C5）、坏校验和（C4）、非法转义（C7）之后都能重新捕获下一条好帧。

### 4.4 容错与计数

| 情况 | 处理 | 计数器（状态条可见） |
|---|---|---|
| 无 `45 44` | 丢弃；仅保留末字节 `0x45`（可能是下帧首字节） | `noiseBytes` |
| 长度域不在 12~256 | 丢弃，skip 1 | **坏帧**（`badLength`） |
| 帧尾提前出现 | 按截断帧丢弃，skip 过该 0x0A | **坏帧**（`truncated`） |
| 收满 len-1 字节后不是 0x0A | 丢弃，skip 1 | **坏帧**（`badTrailer`） |
| 校验和（还原后）不符 | 丢弃，skip 1 | **坏帧**（`badChecksum`） |
| `tlv_len ≠ len-12` | 丢弃，skip 1 | **坏帧**（`badTlv`） |
| `0x09` 后非 `00/01` | 丢弃，skip 1 | **转义错误**（`badEscape`）+ 坏帧 |
| `tlv_len ≠ 1+7×count` | 该帧不产出任何通道数据 | **坏帧**（`badPayload`） |
| 单次 `feed()` 分片 > 4096B | 按 4096 切片增量处理，缓冲区不膨胀 | — |

## 5. 水位换算口径（页面唯一来源，`computeLevels` 900）

```
水位_mm = 挂高_mm（页内设定） − target_distance_mm      （逐通道）
水位_cm = 水位_mm / 10                                  （显示取整，见 §5.3）
```

### 5.1 **不按 presence / target_state 过滤距离**（硬件工程师结论，头号技术风险）

EDV163 是**人体存在检测算法**的衍生品，**静止水面很可能被判「无人」**
（`delay_presence=0`、`target_state=0`）。若页面「只在有人时才取距离」，
静水场景会**长期没有水位数据**。

| 规则 | 实现 |
|---|---|
| 距离一律使用 | `computeLevels`（900）只判断 `0 < distance ≤ 挂高`，**完全不看 presence/state** |
| 无效仅两种 | 距离 = 0（无回波）；距离 > 挂高（超量程） |
| presence/state 只做展示 | 状态条 `h-state-tag`、通道表「presence / 状态」列 |
| 静水面标注 | `stillWater = (presence===0 && state===0)`；界面显示「判定：无人（静水面）」+ 口径行提示「模组按人体存在算法判定为无人，属正常现象；距离照常参与换算」 |
| 自测锁死 | **C9**：`presence=0, state=0, distance=1234` → 水位必须算出 **766 mm = 76.6 cm** |

> 主通道选择（`pickPrimary` 923）：第一个**有效**通道；否则第一个有回波距离的通道；否则第一个通道。
> 多通道时每个通道画各自曲线（不同颜色），主通道加粗 + 标注当前值。

### 5.2 挂高：出厂 **3000 mm**，必须回读校正

| 事实 | 处理 |
|---|---|
| 驱动出厂默认 `0x25 = 3000 mm`；若页面用 2000 换算，水位**整体偏 1 m** | 连上后第 6 条只读查询就是 `GET 0x25` |
| 回读值显示在「设备回报 → 挂高」 | `updateStatusBar` 1701 |
| 回读 ≠ 页内设定 | 配置区**标红**告警「设备挂高（回读 X mm）与设定挂高（Y mm）不一致，水位将整体偏移 ±Z mm」（`#mountWarn`） |
| 用户**尚未手动改过**挂高（`state.mountTouched === false`） | 首次回读时**自动采用**回读值，并写日志；曲线清空（口径变了） |
| 用户已手动改过 | 不自动改，只标红 + 提供「采用设备回读值」按钮（只改页内，不发 SET） |
| 换算始终用**页内设定值** | 主视图「使用挂高 XXXX mm」常显 + 口径行 `换算用挂高 = …`，避免误读 |
| 要让设备也改成页内值 | 「下发配置」写 `0x25 = 页内设定`（逐条等 0xA2） |

### 5.3 精度：只显示整数 cm

EDV163 距离分辨率约 **8 cm**，因此：

- 水位**只显示整数 cm**（大数字、通道表、曲线当前值标签、水位柱百分比）；
- 面积/趋势看的是**相对变化**（注水、排水、液位阶跃），页面明写
  「绝对精度受模组分辨率限制（约 ±8 cm），适合趋势/相对变化，不能当计量级液位计」；
- 原始 `target_distance`（mm）在通道表里保留，仅作诊断字段。

### 5.4 曲线与水位柱

| 元素 | 实现 |
|---|---|
| 时间窗 | 近 **10 分钟**（`CFG.render.windowMs = 600000`），滚动刷新，`pruneSeries` 1930 按时间裁剪 + 数量上限 6000/通道 |
| X 轴 | 6 个刻度，标签为**墙钟时间** `HH:MM:SS`（右端 = 现在） |
| Y 轴 | 0 ~ `Y 轴上限`；默认 **200 cm**（对应挂高 2000 mm），勾选「Y 轴跟随挂高」时自动 = 挂高/10 |
| 满量程参考线 | 挂高/10 处画红色虚线并标注（超出 Y 轴范围时不画） |
| 抽稀 | 单通道 > 1600 点时按步长抽样（`CFG.render.drawPoints`），避免掉帧 |
| 水位柱 | DOM 竖向柱，`fill.height = 水位/满量程 × 100%`；**与曲线同一行、等高**（见 §8.1）：面板 180px、柱宽 124px、左侧 5 档刻度（满/75/50/25/0，按满量程换算成 cm）、柱内上部 24px 粗体百分比、下方「满 XXXcm」+「水位柱」两行居中 |

| 3 | A0 | 0x11 检测延时 | 220 ms | 回报 |

| 5 | A0 | 0x18 工作模式 | 340 ms | 回报 + 顶部状态标签 |
| 6 | A0 | **0x25 挂高** | 400 ms | **回报 + 自动校正换算口径** |

> 运行时兜底：`recordSent`（2043）用**解析器还原后**的 op 判断——若在 `state.writeBusy === false`
> 时出现 SET，`unexpectedSets++` 并在状态条「未确认 SET」显示、日志告警。
> ⚠ 这里不能用固定下标读 `bytes[6]`：msgid/长度里的 `0x0A` 被转义成两字节后下标会错位
> （本版实测踩到并修正）。

### 6.2 下发配置（全页唯一会发 SET 的路径，`requestWriteConfig` 2186）

| 步骤 | 行为 |
|---|---|
| 1 | 未连接/未开模拟 → 直接拒绝，不发帧 |
| 2 | `window.confirm` 列出**每一条**将写的内容；取消 → **一条帧都不发**（日志记「已取消」） |
| 3 | 确认后逐条 `createFrame(0xA1, …)` → 写完**等待应答** |
| 4 | 应答 = `0xA2 REPORT`（msgid 匹配，退化按 type）或 `0xA9 ACK`（状态码 0x01 成功） |
| 5 | 单条 **500 ms** 超时 → **立即中止**，列出失败项，**后续项不再发送** |
| 6 | 任一条被设备拒绝（ACK ≠ 0x01）→ 同样中止并列出原因 |

基础下发（`buildWritePlan` 961，3 条）：`0x25 挂高 → 0x17 上报频率 → 0x18 工作模式`
（先写参数再切模式，避免设备用旧参数按新模式上报）。

**演示用一键配置**（`buildPresetWritePlan` 985，6 条，同一套确认 + 逐条等应答）：

| 顺序 | type | 值 | 依据 |
|---|---|---|---|
| 1 | 0x25 挂高 | 页内设定（默认 2000 mm） | — |
| 2 | 0x26 检测高度 | `0 ~ max(2000, 挂高)` mm | **max 绝不能小于挂高**，否则会把水面本身过滤掉 |
| 3 | 0x27 检测范围 | 运动区/存在区 x,y 各 **±400 mm**（16B） | 硬件工程师推荐 |
| 4 | 0x11 检测延时 | **5 s** | 同上 |
| 5 | 0x17 上报频率 | **10**（=1000 ms） | 同上 |
| 6 | 0x18 工作模式 | **1**（正常） | 同上 |

## 10. 未确认项

| # | 事项 | 现状 / 上板怎么定 |
|---|---|---|
| **U1** | 0x81 每通道 7B 还是 8B | **已裁决：7B**（C 实现 `edv163.c:372-390`；协议文档「8 字节」为笔误）。解析器对 `tlv_len ≠ 1+7×count` 显式失败并提示口径，不猜通道数。上板若真遇到 8B 固件，日志会直接点明，再按需加兼容 |
| **U2** | 周期上报是 `0xA3+0x81` 还是 `0xA2+0x81` | 主路径按 C 实现取 `0xA3`，同时兼容 `0xA2`。上板看日志里 `op=` 即可确认 |
| **U3** | 设备上报帧是否真的做转义 | C 实现接收侧**未还原转义**（`edv163.c:337-345`），说明固件作者可能假定「上报帧里不会出现 0x0A/0x09」，或发送侧确实转义而接收侧只是侥幸。本页按协议文档实现「先还原再校验」。**上板判定方法**：① 看日志里是否有帧标注「N 处转义」（有 = 设备确实转义，本页路径正确）；② 若某帧正文恰含 `0x0A` 而设备**不**转义，本页会把它当成真帧尾 → 该帧判 `truncated` 并重同步（**只丢这一帧，不会污染后续**），此时「坏帧」计数会上升、日志出现「帧尾 0x0A 提前出现」。若实测这种情况频繁出现，需上报硬件/固件侧按协议补转义 |
| U4 | 静止水面是否一定被 `presence` 判 0 | 已按「不用 presence 过滤」实现（U2 风险规避）；上板观察静水时 `presence/state` 实际取值 |
| U5 | 挂高取值对水位的影响 | 设备出厂 3000 mm；本页默认 2000 mm 但**首次回读自动校正**并标红提示。上板确认回读值，再决定默认值是否改为 3000 |
| U6 | 0x26 `max` 与挂高的关系 | 按「max = max(2000, 挂高)」下发；上板确认设备是否接受、水面是否始终落在检测高度窗口内 |
| U7 | 0x02 模块信息的具体字段布局 | 本页只做 ASCII 直显（C 实现按 `device_id[9] + 分隔 + 版本[6]` 解析）；上板看回报文本是否可读 |
| U8 | 设备对 SET 的应答形式 | 本页接受 `0xA2 REPORT`（回显 msgid，±1 容错）或 `0xA9 ACK(0x01)`；上板确认实际是哪种 |
| U9 | 0x11 检测延时最小 2 s | 一键配置写 5 s（≥2），符合 C 实现 clamp |

## 11. 已知限制

### 11.1 环境限制（代码无法绕过）

- Web Serial 需 Chrome / Edge 89+，且 https 或 localhost（`file://` 通常也可）；
  Firefox / Safari 不支持，此时页面提示并只保留「模拟演示」。
- **本环境（沙箱）禁止启动 Chromium 命名管道**，因此本轮**没有**浏览器像素级目检，
  布局只做了静态契约校验（32 项）；真实像素效果需在有桌面的机器上补。
- 串口必须独占：同一端口被串口助手占用时 `port.open()` 会失败并提示。

### 11.2 功能范围限制

| 项 | 说明 |
|---|---|
| 0x28 自动测高 | 不发（会自动改设备挂高，等上板确认后再考虑，且必须走确认流程） |
| 0x29 屏蔽区 | 只认类型名，不解析 13B×N 结构 |
| 0x26/0x27 | 只做回报展示与一键配置下发，不做图形化编辑 |
| 多通道 | 每通道独立曲线；主通道按「第一个有效」规则，不做跨通道融合/平均 |
| 数据留存 | 全部在内存（近 10 分钟）；**不写 localStorage / IndexedDB / Cookie**，刷新即清空 |
| 导出 | 无 CSV/截图导出（本版未要求） |

### 11.3 精度限制

距离分辨率约 **±8 cm** → 水位只显示整数 cm。绝对精度还受安装垂直度、水面波动、
模组自身标定影响；页面定位是**趋势与相对变化**观察工具。

## 12. 设计决策记录

| # | 决策 | 理由 | 备选与否决原因 |
|---|---|---|---|
| D1 | 解析器自带流式还原（`_tryDecode` 750），不先整段 `unescapeBytes` | 半帧时不必反复拷贝，内存恒定；错误定位到具体字节 | 「先整体还原再解析」在半帧/截断时会破坏缓冲区语义 |
| D2 | 坏帧一律 **skip 1 字节** 重同步 | 最坏情况只丢 1 字节，能穿过截断/坏校验和继续工作 | 「整帧丢弃」会在长度域被污染时丢一大段 |
| D3 | 0x81 步长**钉死 7B**，不做 7/8 自动容错 | 猜错会静默渲染垃圾数据；显式失败 + 明确报错更好维护 | 「按 `tlv_len/count` 自适应」= 把文档笔误洗成数据 |
| D4 | **不按 presence/state 过滤距离** | 静水面会被判「无人」，过滤会导致长期无数据（头号风险） | 「有人才取距离」在静水场景不可用 |
| D5 | 挂高**首次回读自动采用**（仅在用户未手动改过时） | 出厂 3000 与默认 2000 差 1 m，静默偏 1 m 比误改更糟 | 「只标红不自动改」仍需用户理解公式 |
| D6 | 水位只显示**整数 cm** | 分辨率 8 cm，0.1 cm 是虚假精度 | 「保留 1 位小数」会给出不存在的精度 |
| D7 | `recordSent` 用解析器取 op/type | 转义会让固定下标错位，曾导致误判 | `bytes[6]` 直读（EDV11P 无转义才安全） |
| D8 | 一键配置独立成 6 条计划，但走**同一套**确认 + 逐条等应答 | 不新增任何绕过确认的写入路径 | 「一键静默下发」违反默认只读 |
