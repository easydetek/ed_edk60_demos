## 二、上板受阻的实证记录（写清楚，便于后续接手）

| 项 | 实测 |
|---|---|
| 现象 | 20 s 收到 29,503 B，但 `0x45 0x44` 帧头 **0 次**、`0x0A` **0 次** |
| 字节分布 | 只集中在 8 个值：`F8`(9639)、`3E`(4844)、`FE`(4111)、`00`(3521)、`C6`(3370)、`06`(2334)、`38`(1191)、`C0`(446) |
| 主动探测 | 发 `GET 0x02`（`45 44 00 0C 01 00 A0 02 00 00 38 0A`）与 `GET 0x25`，**无任何合法应答** |
| 原因 | 用户确认：**该模组当前烧的是「挥手」固件**，不是水位/测距版 |
| 处置 | 需向雷达固件负责人索取 **EDV163 水位/测距版二进制固件**并烧录后，才能跑上板用例 |

## 四、对外口径红线（发布期间必须遵守）

**可以写**：
- 「固件把 EDV163 的串口数据原样送到 USB，浏览器直接显示水位曲线」
- 「协议要点：256000、帧尾 0x0A、正文转义、`op=0xA3/type=0x81`、每通道 7B、水位 = 挂高 − 距离」
- 「已通过无硬件自测；**尚未在实物上实测**」

**不得写**：
- 任何具体帧率/坏帧率/水位精度/漂移数字（当前**没有实测值**）
- 「精度 ±2 cm」之类（分辨率约 ±8 cm，且未标定）
- 「已解决静水面漏检」「支持任意量程」（量程限 1200~5000 mm 挂高）
- 「转义已实机验证」（U3 未定）

## 五、与 EDV11P 的流程差异（经验沉淀）

1. 本次**先做了协议矛盾排查**（8B vs 7B），避免了整套解析器返工 —— 建议后续新模组沿用「先用驱动源码核对文档」这一步。
2. 本次**上板被模组固件卡住**，与 EDV11P 的"型号分支"风险同源：**拿到模组第一件事应是回读模块信息 + 看帧头**，而不是先烧固件。
3. 网页工具在无实测数据的情况下，通过「模拟演示 + 桩环境 + 布局契约」三级自测把可验证部分做到位 —— 这套自测骨架对后续新传感器可直接复用。
