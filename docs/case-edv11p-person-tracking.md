在通道、门口、走廊这类地方做**人数统计与轨迹跟踪**，最常见的做法是装摄像头——但它会采集画面，遇到宿舍、卫生间门口、办公工位这些位置，隐私问题往往比技术问题更难谈。

我们用 **EDK60 开发板**（ESP32-C6）桥接 **EDV11P 侧装雷达模组**，做了一套**只输出坐标、不输出图像**的参考方案：雷达测得的人数和每个人的 x/y/z 坐标，经 UART 进 ESP32-C6，再由**芯片原生 USB** 直送电脑——不需要 USB 转串口芯片，PC 端不需要装任何驱动。

连续跑满 30 分钟的真实采集结果：**15,483 帧有效帧、坏帧 0、重同步 0、帧完整率 100%；检测人数 1~6 人，共出现 6 个目标 ID**。

> **口径说明（必读）**：「帧完整率 100%」= 好帧 /（好帧 + 坏帧 + 重同步）；坏帧为 0 时该值恒为 100%，**它不度量「漏帧」**。统计窗口从采集开始后 10 s 起算（前 2,970 字节为板子开机引导日志，落在窗口外）。准确说法是：**30 分钟、本机 USB-C 直连（未接 DC 适配器）、统计窗口内没有坏帧与重同步**，而不是「绝不丢帧」。
> 
> **目标 ID 说明**：ID 1 在 15,454 个上报帧中出现 15,430 帧（99.8%），**模组会复用 ID**；轨迹图按 ID 连线只代表「该 ID 的坐标序列」，**不代表同一个自然人**。人数请以每帧的 count 字段为准。

## 场景需求

| 需求 | 说明 | 方案如何满足 |
|---|---|---|
| 隐私合规 | 现场不允许采集人脸或画面 | 60 GHz FMCW 雷达，输出的是「第几个目标、坐标是多少」，**没有任何图像数据** |
| 不只是"有人/无人" | 甲方要的是**当前几个人**，以及人在哪儿 | 0x70 目标上报帧携带每个目标的 ID 与 x/y/z 坐标 |
| 一台设备覆盖一条通道 | 点位越少越好装、越好维护 | 侧装单点：配置范围 x ±500 cm、y 0~800 cm（设备回读值） |
| 光照/温度无关 | 夜间、逆光、戴口罩都不影响 | 雷达不依赖可见光 |
| 免驱动接入 PC | 客户现场（尤其是只有云桌面/受控电脑的环境）不能装驱动 | ESP32-C6 原生 USB CDC，插上就是串口 |
| 上位机可自由替换 | 客户已有自己的后台或第三方上位机 | 桥接固件**纯字节透传**，不做任何协议加工 |

**为什么是侧装而不是顶装**：顶装（朝下）时，人的头顶与雷达正下方存在几何盲区，且"离摄像头多远"和"离雷达多远"是两件事，现场解释成本高；侧装把设备装在通道端头的墙面或立柱上（本方案为**绕 +y 倾斜 60°、主轴俯角 30°、挂高 200 cm**），主视轴沿通道向前，y 轴直接就是"沿通道走了多远"，轨迹长度可用满 800 cm。

## 方案构成

```text
EDV11P 侧装雷达模组
   │  UART 921600 8N1（模组 TX → IO4，模组 RX ← IO5）
   ▼
EDK60（ESP32-C6）——纯字节双向透传：不解析、不注入、不打印
   │  芯片原生 USB CDC（免驱动）
   ▼
PC / 浏览器（Python 上位机，或 Web Serial 网页版工具）
```

| 环节 | 器件 / 技术 | 关键点 |
|---|---|---|
| 感知 | EDV11P 侧装版雷达 | 主动上报 0x70 目标帧：感应区编号、目标数、每个目标的 ID 与 x/y/z（int16，单位 cm） |
| 主控 | ESP32-C6（EDK60 开发板） | UART1 与模组通信，原生 USB 与 PC 通信，两路各自独立 |
| 连接 | 芯片原生 USB Serial/JTAG | 省掉 USB 转串口芯片、外部晶振与电平转换；波特率对 USB CDC 不敏感 |
| 上位机 | Python 脚本 / 任意串口工具 / 浏览器 | 帧同步、校验、解析全部在 PC 侧完成 |

## 接线与安装

| 信号 | EDK60 侧引脚 | 模组侧 | 说明 |
|---|---|---|---|
| 模组 TX → MCU RX | **IO4** | H3 排针 `T` 脚 | 数据入口（雷达 → PC 全靠这条线） |
| 模组 RX ← MCU TX | **IO5** | H3 排针 `A` 脚 | 下发配置命令（本方案由上位机发，固件不代发） |
| 雷达电源使能 | **IO14** | — | 输出高 = 3.3V_RADAR 上电；本方案常高 |
| 电源 / 地 | `V`(3V3) / `G` | `V`/`P` / `G` | 必须共地 |
| 串口参数 | 921600 / 8N1，无流控 | — | 实测 9 档波特率扫频，仅此档有数据 |

:::warning 模组必须插 H3，不要插 H4
板上 H3 与 H4 两个 8 pin 排针**信号集合相同但顺序相反**：
H3 = `RES A R T G V P`，H4 = `RES P V G R T A`。
H4 的 `T` 脚与电源使能是同一个网络，插 H4 会让电源与数据互相干扰。
**请插 H3。**
:::

安装与坐标口径（以下均为**设备回读值**，不是文档推断值）：

| 项 | 值 | 来源 |
|---|---|---|
| 安装方式 | 侧装：绕 +y 倾斜 60°、主轴俯角 30° | 机械安装参数 |
| 挂高 | **200 cm** | GET 0x22 回读 `00C8` |
| 检测范围 | x ∈ [−500, +500] cm、y ∈ [0, 800] cm | GET 0x20 回读 `FE0C 01F4 0000 0320` |
| 检测高度 | 30 ~ 200 cm | GET 0x21 回读 `001E 00C8` |
| 坐标语义 | x = 水平横轴，y = 离墙距离（0 = 墙面/雷达侧），z = 离地高度 | 侧装口径 |

本次 30 分钟实测的目标落点范围：**x −113 ~ 116 cm、y 2 ~ 721 cm、z 30 ~ 200 cm**。60°/30° 是**机械安装参数**，不是软件要做的旋转矩阵——协议里没有倾角参数，上位机也不做三角变换。

> **z 的口径（推断，非标定结论）**：实测 z 恰好铺满配置的检测高度区间（30~200 cm，最小值贴 30、多个最大值贴 200），这与「z = 离地高度」一致，**但也可能是被检测窗口裁剪后的量**。本方案未做地面卷尺标定，因此表述为「z 与人体离地高度区间吻合」，**不宣称已完成绝对高度标定**。这一点在方案设计阶段最容易写反：协议里没有任何倾角或旋转参数，60°/30° 只存在于机械安装图上。

一个容易被忽略的细节：这份采集里还有 29 帧 `0xA2/0x05`（工作模式上报），它用的是**另一条 msgid 序列**。若把两种帧混在一起看 msgid 连续性，会得到 58 次"跳号"（0.37%），看起来像丢帧；按 `(op, type)` 分组后，每个组的跳号都是 **0**。结论是 msgid 按命令类别独立计数，桥接本身一帧没丢。

补充一句判据口径：捕获脚本在 1,800 s 到点时于帧中间关闭串口，最后一个字节（`0x45`，偏移 530,971）凑不满一帧，被归为"尾部残留"。这是**采集边界效应**，不是丢帧（坏帧 0、重同步 0）。它在洁净性判据里表现为 1 字节未归属（528,002 字节统计窗口中的 1 字节，比率 1.9×10⁻⁶），属于**告警级**、不改变通过结论——但必须写进报告，否则"数据流洁净"这句话会被误读成"连尾字节都不存在"。稳态 30 分钟内真正属于设备的非协议字节是 **0**。

## 关键工程点

### 1. 纯字节透传为什么可行

固件里**没有一行协议代码**：没有 `0x45`/`0x44` 常量、没有校验函数、没有 msgid 追踪。它只做一件事——UART 收到的字节原样写进 USB，USB 收到的字节原样写进 UART。

这么做的收益：协议升级、换型（EDV151 ↔ EDV11P）、换上位机，固件一行都不用改；桥接的正确性可以被压缩成一个极简的命题——**「进来的字节流和出去的字节流是否完全相同」**，而这恰好是 PC 侧可以客观统计的（未归属字节数、坏帧数、重同步数、msgid 连续性）。

代价同样明确：桥不提供任何语义保障，**校验必须由上位机做**。所以本项目配套了帧校验工具，把"有没有丢字节/有没有把帧搞乱/有没有别的东西混进流里"变成三项可判定指标，而不是靠"看起来正常"。

### 2. 零日志污染的四道保险

这是整套方案里最反直觉、也最容易翻车的一处：**帧头 `0x45 0x44` 正好是 ASCII 的 `ED`**——而板名 `EDK60` 的前两个字母就是 `ED`。固件只要往同一条 USB 打一行带项目名的日志，解析器就会把它当成帧头，接着把后面的 `K6`（`0x4B 0x36`）当成帧长，报"长度非法"并丢字节，一次假同步就凭空产生了。

所以"不打日志"必须做成四道互相独立的保险，任何一道失效都不至于污染数据流：

| 道 | 做法 | 兜住什么情况 |
|---|---|---|
| ① 编译期 | `CONFIG_LOG_DEFAULT_LEVEL_NONE=y`，日志宏在编译期消失 | 所有 `ESP_LOG*` 调用点 |
| ② 编译期 | 关掉启动横幅与引脚表打印（这两处是 `printf` 型，日志级别管不到） | 上电瞬间的文本输出 |
| ③ 源码 | 透传 demo 里**零** `printf`/`ESP_LOGx`；诊断信息改写 UART0 且默认关闭 | 开发者顺手加的调试输出 |
| ④ 运行期 | demo 首行执行 `esp_log_level_set("*", ESP_LOG_NONE)` | 用户自己 `menuconfig` 编译、没走 demo 专用默认配置 |

:::danger 不要用"关掉第二控制台"来实现静音
`CONFIG_ESP_CONSOLE_SECONDARY_NONE` 会连带关掉 USB Serial/JTAG，实测结果是**系统启动卡死、USB 不枚举**、必须拔插复位。
正确做法是**保留控制台、但不产生任何字符**。
:::

这套四道保险的效果是可测的：本次 30 分钟采集里**一个非协议字节都没有**（除末尾 1 字节采集截断），没有任何固件文本。

### 3. 校验和手算的坑

协议规则本身很简单：`CS = 帧头起所有字节求和 & 0xFF`。但"简单"不等于"手算不出错"，本项目栽过两次：

1. **联调首轮 `GET` 命令完全无应答**，排查一圈接线与电源后才发现是手算校验和写错——`GET 0x02` 的 CS 应为 `0x58`，实际发出的是 `0x35`。设备按规则静默丢弃坏帧，于是症状看起来像"设备没反应"。
2. **协议文档里两条 `GET` 示例的 CS 比规则算出来的大 4**（等价于按 `LEN = 0x0F` 而不是 `0x0B` 计算）。照抄文档示例，就会自己造出坏帧。

结论：**组帧一律程序化，不要手抄、不要心算**。上位机侧的校验也同理，用同一份代码算，不要拿两套实现互相对照后就假定自己是对的。

### 4. H3 / H4 插错会同时坏电源和数据

板上两个 8 pin 排针信号集合相同、顺序相反：H3 = `RES A R T G V P`，H4 = `RES P V G R T A`。H4 的 `T` 与电源使能是同一网络，插上去会让电源与数据互相干扰。这个坑的症状是"能上电、偶尔有数据、然后就没有了"，很容易被误判成串口参数或雷达坏了。**认准 H3。**

## 已知边界

写清楚没做的部分，比写清楚做了的部分更重要：

| 边界 | 现状 |
|---|---|
| 人数范围 | 只验证了 **1~6 人**的常规场景。更密集的人群（>6 人）、快速交叉穿越、贴身并行未验证 |
| 无人场景 | 本次 30 分钟内**没有出现 0 人帧**（人数最小值 1）。因此"人走空后人数清零"的行为**未验证** |
| 长期稳定性 | 只做了 **30 分钟**连续采集，未做 7×24 老化、未做温漂与长时间漂移测试 |
| 几何标定 | 未做地面画十字的标定用例；轨迹是**设备坐标系下的相对位置**，"轨迹与实际走位偏差 < 30 cm"这一项未验证 |
| 时间精度 | 离线捕获文件无逐帧时间戳，横轴时间按帧序线性插值；逐帧到达间隔分布未统计 |
| 网页工具 | Web Serial 只在 Chromium 系浏览器（Chrome / Edge 89+）提供，且需 https 或 localhost 安全上下文、首次需用户授权选择串口；网页版轨迹工具的真实浏览器与真机联调，截至本文写作时**未完成**（桌面端 Python 上位机已实测通过） |
| 型号分支 | EDV11P-N 系列的 `-02`（人数统计/轨迹）与 `-03`（跌倒+存在）分支定义**以设备 `GET 0x02` 回读为准**，不要按订货型号推断。本方案所用模组回读为 `EDV11P_VA,V1.3.3,0x95F0`，0x70 带坐标稳定上报 |
| 侧装支持 | 协议里**没有**倾角/旋转参数，0x20/0x21/0x22 都是俯视正交坐标系参数。本台模组的 0x70 坐标实测为侧装口径（z 落在人体高度区间），但这一能力无书面依据，换批次/换固件必须重测 |
