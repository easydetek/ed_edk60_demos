# 用 ESP32-C6 + EDV151 毫米波雷达做一台「呼吸心率监测仪」

> **一句话**：一块 ESP32-C6 开发板 + 一颗 EDV151 生命体征雷达，**不用任何转串口芯片、不用装驱动**，
> 把心率、呼吸率、人体距离实时送到 PC 上位机。

---

## 1. 先看结果（30 秒）

接好线、烧好固件，PC 上打开串口，你会看到这样的实时输出：

```text
睡眠状态 = 1（清醒）      距离 = 58 cm      体动 = 5
心率     = 75 bpm          呼吸率 = 21 bpm
心率状态 = 0（正常）       呼吸状态 = 0（正常）
心率可信度 = 2             呼吸可信度 = 2
```

数据每秒上报一次，校验零错误。人坐在雷达正前方约 60cm、保持接近静止，**约 20~40 秒**后心率与呼吸率就会稳定输出。

### 你会得到什么

1. **一条完整的可复现链路**：EDV151 →(UART 921600)→ ESP32-C6 →(原生 USB)→ PC，全部代码开源
2. **实测确认的引脚表**（含一处原理图标注歧义的定论）
3. **EDV151 串口协议**的完整用法：帧结构、校验、6 条开机握手命令
4. **关键调参经验**：为什么出厂参数下心率呼吸**永远是 0**，以及怎么一招解决
5. **3 个配套 PC 工具**：体征验收、通用监视、直接给模组下命令

## 3. 硬件：引脚必须实测，不要只信原理图

### 3.1 实测引脚表

| 信号 | 引脚 | 验证方式（本文实测） |
|---|---|---|
| 模组 **TX → MCU RX** | **IO4**（H3 的 `T` 脚） | 收到合法帧 `5A 0F 00 "radar_ready" 05` |
| 模组 **RX ← MCU TX** | **IO5**（H3 的 `A` 脚） | 发 `get_version` 收到 `5A 07 80 "166" EC` |
| 雷达**电源使能 EN** | **IO14** | 拉高/拉低时丝印 `RADAR` 的**红灯**同步亮/灭 |
| 橙色指示灯（丝印 `L`） | IO15 | 仅指示灯，**与电源 EN 无关** |
| 雷达电源轨 | 3.3V_RADAR（U4 = AP7362-33SP-13） | 由 IO14 使能；红灯接在该轨上 |
| 串口参数 | **921600 / 8N1** | 9 档波特率扫频，仅此档有数据 |

> **⚠ 重要** 我们最初读图得到的结论是「EN=IO15、雷达 RX=IO14」——**两个都是错的**。
> 实测把 UART 的收发脚和电源脚全部纠正了一遍。**请以本节表格为准。**

![图 1 · EDK60 开发板与 EDV151 模组连接实拍](../../assets/edv151/01-board-overview.jpg)

*图注：模组插在 **H3** 排针上；此时丝印 `RADAR` 的红灯应点亮，表示 3.3V_RADAR 已上电。*

### 3.2 为什么要插 H3 而不是 H4

板上有两个 8 pin 排针，信号集合相同但**顺序相反**：

| 排针 | 引脚顺序 | 数据脚 |
|---|---|---|
| **H3**（用这个） | `RES A R T G V P` | `T`=IO4、`A`=IO5 |
| H4 | `RES P V G T R A` | `T` 与 EN **同网络** |

H4 的 `T` 脚和电源使能撞在一起，插 H4 会导致**电源与数据互相干扰**。所以模组请插 **H3**。

### 3.3 没有万用表怎么确认引脚

本文全程没用万用表，靠三个软件手段定位：

| 要确认什么 | 手法 |
|---|---|
| 电源使能是哪根脚 | 让候选脚**周期性拉高/拉低**（1Hz），肉眼观察丝印 `RADAR` 的红灯是否同步闪烁 |
| 模组 TX 是哪根脚 | 把候选脚逐个配成 UART RX，看哪根能收到 `0x5A` 开头的合法帧 |
| 模组 RX 是哪根脚 | 向候选脚逐个发送 `get_version` 封包，看哪根能收到版本号应答 |

## 4. 复现步骤

> 每一步都给出**预期结果**与**验证点**，出现偏差请直接跳到第 7 节排查表。

### 步骤 1 · 插好模组，确认上电

把 EDV151 插到 **H3**，用 USB-C 连 PC。

**预期结果**：板子上 **绿灯**（3.3V 常亮）亮；橙灯（丝印 `L`）与红灯（丝印 `RADAR`）此时可能都不亮。

**验证点**：设备管理器 / `ls /dev/tty*` 能看到一个 **USB 串行设备**（VID `303A`）——这就是 ESP32-C6 的原生 USB，**不需要任何驱动**。

### 步骤 2 · 拉取工程并选择 demo

```bash
git clone <你的仓库地址> edk60_demos
cd edk60_demos
idf.py set-target esp32c6
idf.py menuconfig
```

在 `EDK60 Demo` 菜单里选择 **`5.1 radar_bridge`**。

**验证点**：`idf.py menuconfig` 保存后，`sdkconfig` 中应出现：

```text
CONFIG_APP_EDK60_DEMO_RADAR_BRIDGE=y
CONFIG_APP_EDK60_BRIDGE2_RX_PIN=4
CONFIG_APP_EDK60_BRIDGE2_TX_PIN=5
CONFIG_APP_EDK60_BRIDGE2_BAUD=921600
```

### 步骤 3 · 编译并烧录

```bash
idf.py build
idf.py -p COM6 flash
```

（Linux/macOS 把 `COM6` 换成 `/dev/ttyACM0` 之类。）

**验证点**：末尾出现 `Hash of data verified.` 与 `Hard resetting via RTS pin...`。

### 步骤 4 · 确认模组上电

看板子上丝印 `RADAR` 的**红灯**。

**预期结果**：**红灯亮起**。

**验证点**：红灯亮 = 3.3V_RADAR 已建立 = 模组已上电。
如果红灯不亮，说明电源使能没生效，请检查固件是否把 `IO14` 拉高了（见第 7 节）。

### 步骤 5 · 确认模组在做开机握手

打开串口监视器（115200），会看到固件逐条发握手命令并收到 `ok`：

```text
握手 turn_on（开射频）              写11字节  应答6字节 ok
握手 set_time（校时）               写23字节  应答6字节 ok
握手 set_para 4:1（上报周期 1 秒）   写16字节  应答6字节 ok
握手 set_para 5:30,6:150（检测范围）  写23字节  应答6字节 ok
握手 set_gain 0.5（降低灵敏度）      写16字节  应答6字节 ok
握手 set_boost 2（中心增强）         写15字节  应答6字节 ok
握手完成：模组应开始定时上报 vital_signs 体征帧
```

**验证点**：**6 条全部 `ok`**。
其中第 5、6 条（`set_gain` / `set_boost`）是能否算出心率呼吸的**关键**，第 6 节会详细解释。

### 步骤 6 · 在 PC 上收数据

用配套的验收工具（推荐）：

```bash
python tools/radar_watch.py --port COM6
```

或者用任意串口助手打开该端口——**波特率随便填**，因为走的是 USB CDC，不依赖波特率。

**预期结果**：

```text
[   5.2s] 距离=  0cm  体动=   0  心率=  0bpm  呼吸=  0bpm  ← 没检测到人，请坐近一点/正对雷达
[  20.7s] 距离= 43cm  体动=   4  心率=  0bpm  呼吸=  0bpm  ← 已检测到人，保持静止等心率/呼吸率
[  28.3s] 距离= 43cm  体动=   4  心率=  0bpm  呼吸= 18bpm  ← 呼吸率先出来
[  31.6s] 距离= 43cm  体动=   3  心率= 84bpm  呼吸= 18bpm  ← 心率也出来了 ✅
```

**验证点**：`距离 > 0` 说明检测到人；`心率 > 0 且 呼吸率 > 0` 说明体征算法已锁定。

![图 2 · PC 上位机实时输出界面](../../assets/edv151/02-monitor-output.jpg)

*图注：每秒一行状态，`距离` 先出现，随后 `呼吸率`、`心率` 依次稳定；`可信度 ≥ 2` 时数据基本可信。*

### 步骤 7 · 坐好，等 20~40 秒

这是最容易被忽略的一步：

- **坐到雷达正前方 30~150cm 内**，胸口尽量正对雷达
- **保持接近静止**（体动值要 < 5）
- 正常呼吸，不要憋气也不要刻意深呼吸
- 等待 **20~40 秒**让算法累积信号

**验证点**：`体动` 稳定在 1~5，`心率` 在 48~120 之间，`呼吸率` 在 9~48 之间。

## 5. 串口协议速查（EDV151）

### 5.1 帧结构

```text
+------+--------+--------+---------------+--------+
| 0x5A |  LEN   |   ID   |    PAYLOAD    |  XOR   |
+------+--------+--------+---------------+--------+
```

| 字段 | 说明 |
|---|---|
| `0x5A` | 帧头 |
| `LEN` | **整帧字节数**（含帧头与校验） |
| `ID` | `0x00~0x7F` = 雷达上报；`0x80~0xFF` = 主控请求（应答沿用请求 ID） |
| `PAYLOAD` | ASCII 字符串 |
| `XOR` | 前面所有字节依次异或 |

实测样例：

```text
5A 0F 00 "radar_ready" 05     ← 上电就绪（雷达主动发）
5A 0C 01 "get_time"    6B     ← 请求主控校时（每小时一次）
5A 06 81 "ok"          D9     ← turn_on 的应答
5A 07 80 "166"         EC     ← get_version 的应答（固件版本 166）
```

### 5.2 开机必做的 6 条命令

| # | 命令 | 作用 | 不发会怎样 |
|---|---|---|---|
| 1 | `turn_on` | **开射频** | 永远只有 `radar_ready` / `get_time`，没有体征数据 |
| 2 | `set_time <epoch>` | 校时 | 雷达每小时会来问时间，不影响体征但建议设 |
| 3 | `set_para 4:1` | 上报周期 1 秒 | 用默认周期 |
| 4 | `set_para 5:30,6:150` | 检测范围 30~150cm | 用默认范围 |
| 5 | **`set_gain 0.5`** | **降低灵敏度** | 见第 6 节，**心率呼吸恒为 0** |
| 6 | **`set_boost 2`** | 中心增强 | 同上 |

改完参数想掉电保存，追加一条 `save_para`。

### 5.3 体征数据帧

```text
vital_signs <睡眠状态>,<距离cm>,<体动>,<心率bpm>,<呼吸率bpm>,
            <心率状态>,<呼吸状态>,<心率可信度>,<呼吸可信度>
```

| 字段 | 范围 | 说明 |
|---|---|---|
| 睡眠状态 | 0~5 | 0 离床 / 1 清醒 / 2 REM / 3 浅睡 / 4 深睡 / 5 翻身 |
| 距离 | 0~255 | cm，0 = 未检测到人 |
| 体动 | 0~255 | 越大越剧烈，**静息时应 < 5** |
| 心率 | 0, 48~120 | bpm，**0 = 未识别** |
| 呼吸率 | 0, 9~48 | bpm，**0 = 未识别** |
| 心率/呼吸状态 | — | 0 正常，其余为过慢/过快/呼吸暂停等 |
| 心率/呼吸可信度 | 0~4 | 越高越可信，建议 ≥ 2 再采信 |

## 6. 最关键的一条经验：增益过大会让心率呼吸恒为 0

这是整个项目里**最难定位**的问题，现象看起来像硬件坏了，实际只是两个参数。

### 现象

- 雷达**能稳定检测到人**：`距离 = 43~58cm` 一直有值
- 但 `心率 = 0`、`呼吸率 = 0`，**一直不出数**
- 关键线索：`体动` 一直在 **20~60** 之间（人明明坐着不动）

### 根因

体征算法要求**静息体动 < 5** 才肯计算心率/呼吸。出厂参数 `gain=4 / boost=0` 灵敏度过高，
把呼吸、心跳之外的微小扰动都算成了「体动」，于是算法认为目标在动，永远不算体征。

### 解法

```bash
# 用配套工具直接给模组下命令
python tools/radar_cmd.py --port COM6 "set_gain 0.5" "set_boost 2" save_para
```

### 效果对比（同一人、同一位置）

| 参数 | 体动 | 心率 | 呼吸率 |
|---|---|---|---|
| 出厂 `gain=4 / boost=0` | 20~60 | **0（永不识别）** | **0（永不识别）** |
| 调整后 `gain=0.5 / boost=2` | **1~6** | **75 bpm** | **21 bpm** |

> 官方协议文档里也写了这条调参准则：「调整增益，使**静息体动 < 5**、大幅活动体动 > 200」。
> 如果你的场地仍出不了数，优先继续小幅降低 `gain`。

## 7. 排查表

| 现象 | 可能原因 | 处理 |
|---|---|---|
| 红灯（丝印 `RADAR`）不亮 | 电源使能没生效 | 确认固件把 **IO14** 拉高；确认模组插在 **H3** |
| 一个字节都收不到 | 模组没上电 / 插错排针 | 看红灯；把模组换到 H3 |
| 只收到 `radar_ready` / `get_time` | **射频没开** | 补发 `turn_on` |
| 收到大量乱字节，校验全失败 | 波特率不对 | 改回 **921600** |
| `距离 = 0` 一直不变 | 没检测到人 / 超出范围 | 坐到 30~150cm 正前方；检查 `set_para 5/6` 范围 |
| `距离 > 0` 但心率呼吸恒 0 | **增益过大**（见第 6 节） | `set_gain 0.5` + `set_boost 2` |
| 体动一直很大 | 桌面/支架有震动，或人在动 | 固定好模组；人保持静止 |
| 烧完不启动、USB 不枚举 | 关闭了 USB 第二控制台 | 见 8.3 第 1 条 |
| 每次抓日志都只看到启动过程 | 打开串口会复位板子 | 打开后立刻清 DTR/RTS，或把采集窗口放到启动之后 |
| 日志卡在某一行不再输出 | UART 发送/接收锁死锁 | 把开机握手放在启动数据搬运任务**之前** |

## 8. 复盘：几个关键决策与真实踩坑

### 8.1 为什么用「原生 USB」而不是 USB 转串口

ESP32-C6 自带 USB Serial/JTAG，**免驱动、免外部晶振、免电平转换**。
少一颗 CH340 就是少一颗成本、少一个驱动安装步骤。代价是：它只有**一个** USB 外设，
日志和业务数据会抢同一条通路（见 8.3 第 1 条）。

### 8.2 为什么固件要内置握手命令，而不是让上位机发

`turn_on` / `gain` / `boost` 这些是**上电必须做一次**的动作。
放在固件里做，用户接上 USB 就能直接看到数据，上位机只管收——这才叫「开箱能用」。

### 8.3 踩坑清单（现象 → 根因 → 解法）

| # | 现象 | 根因 | 解法 |
|---|---|---|---|
| 1 | 为了「让 USB 上只有数据」而关闭 USB 第二控制台，结果**系统启动卡死**，连 `main_task` 都不启动，USB 不枚举，必须拔插 | 该选项会让 `USJ_ENABLE_USB_SERIAL_JTAG` 连带关闭，USB 模块时钟在启动阶段被关 | **不要关 USB 控制台**；改用「不产生日志字符」的方式让数据干净 |
| 2 | `gpio_set_level(pin,1)` 后 `gpio_get_level(pin)` **永远读到 0**，电源状态一直误报「关闭」 | 纯 `GPIO_MODE_OUTPUT` 时输入通道关闭，回读无意义 | 需要回读的脚改用 `GPIO_MODE_INPUT_OUTPUT` |
| 3 | 自动扫脚时把 6 个候选脚全扫一遍，**全部 0 字节**，像「模组不输出」 | 扫描时把**电源使能脚释放成高阻输入**，雷达整段扫描期间都在掉电 | 扫描期间**保持 EN 输出高**，并把 EN 脚从候选列表剔除 |
| 4 | 检测到人但心率呼吸**恒为 0** | 增益过大 → 静息体动 20~60 > 阈值 5 | `set_gain 0.5` + `set_boost 2` |
| 5 | 自动识别选中了**悬空脚**而不是真实信号脚 | 判据只看「字节数最多」，悬空脚噪声（167 字节）打败了真实信号（73 字节） | 判据要结合帧头是否合法；**人工确认后直接写死配置、关掉自动识别** |
| 6 | 某根脚 0 字节，误判成「没信号」 | 波特率不匹配时 UART 会丢弃全部字节 | **引脚扫完还要扫波特率** |
| 7 | 发完命令后日志停住不再输出 | `uart_flush_input()` 与数据搬运任务的 `uart_read_bytes()` 争锁死锁 | 开机握手放在**启动搬运任务之前** |
| 8 | Kconfig 里关掉一个 bool 后编译报 `CONFIG_XXX undeclared` | Kconfig 语义：`default n` 的 bool **不生成宏** | C 里一律用 `#ifdef` 兜底 |
| 9 | 改了 Kconfig 但新符号不出现 | `idf.py` 不会因 Kconfig 变化强制重建已有 `sdkconfig` | 构建前删掉该 demo 的 `sdkconfig` |
| 10 | 打开串口板子就重启，永远只抓到启动日志 | 打开串口时 DTR/RTS 被拉低触发复位 | 打开后立刻清 DTR/RTS |

### 8.4 数据与测量条件

| 项 | 值 | 测量条件 |
|---|---|---|
| 心率 | 75~84 bpm | 成年男性静坐，距雷达 43~58cm，室温，静息 |
| 呼吸率 | 18~21 bpm | 同上 |

## 10. 后续可以做什么

- **做 Sleep 报告**：模组还会在睡眠结束后上报 `sleep_quality` 帧（评分/效率/各睡眠阶段占比），可做成日报
- **上云**：ESP32-C6 支持 Wi-Fi 6，把体征数据推到 MQTT / 私有服务器
- **低功耗**：雷达电源已可软控（IO14），配合 deep sleep 做电池版
- **多目标**：换用支持多目标的雷达型号，协议族相同，改动量小
